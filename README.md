# OVERLOAD

洗練された上質な肉体を作るための、トレーニングプロデュース PWA。自分専用。

目的はボディビルや競技ではなく**ボディメイク**。見た目の質が上がることが成功で、
扱う重量はそのための手段として扱う。ただし手段は正確に管理する——というのがこのアプリの立場。

- **目標を出さない。** 入力欄には前回と同じ数字が入っているだけ。上げても下げてもただの記録として残る
- **前進があったときだけ祝う。** 記録を更新した瞬間にアニメーションが出る（条件は下に文献つきで書いた）
- **サイクルの現在地を出す。** 同じ負荷で何回目か・上限レップに何セット届いたか。
  全セット届いたら「**卒業**」と次の負荷を提示する（提示するだけで、入力欄には入れない）
- **復帰を数える。** 週連続だけでなく、空いた週から戻った回数と通算回数を出す
  ——切れない記録より、途切れても戻れること
- 部位・押す/引く・前面/背面の **3 軸で直近 4 週の偏り**が見える。0 セットの部位も行ごと出す
- **1 日の終わりに一度だけまとめる。** 「今日を終える」を押すと、その日の数字と動いた記録が
  出る。讃える一言はその日の記録から出る事実の言い換えで、何をしても同じ文にはならない
- **重さを設定しない種目**（自重・アシストマシン）は、入力欄の意味ごと切り替える
- その日を**1 枚の画像**に組んで共有できる（送り先はアプリではなく端末の共有シート）
- 体重は毎日つける前提で画面の一番上。別タブで折れ線が見られる
- **記録を延ばした予想**を、体重にも種目の到達点にも赤い点線で添える。目標ではないので
  外れても何も起きない。伸びが鈍ることも入れてあるので、**無限に落ちる線にはならない**
  （体重は身長から出す BMI の帯へ、種目の重量は体重比の上限へ漸近する）
- 種目ごとに**やり方・効く筋肉の図・一般的なコツ**と、**自分用の機材設定メモ**を持つ
- メモは**セットごと / その日のその種目 / その日全体**の 3 段階
- **アシストマシン**（数字を下げるほど負荷が上がる）を専用の扱いで入力できる
- 圏外でも開けて操作できる。記録は Firestore にも同期され、端末を失っても残る
- 記録をまとめて Claude に渡し、続けるための助言をもらえる
- 記録が無くても中身が見られる（**サンプルの 9 週間**。触っても何も保存されない）
- サーバー費用 0 円（GitHub Pages + Firestore の無料枠）

## 1. 目標を出さず、前進だけを祝う

### 1.1 なぜ目標をやめたか

以前はダブルプログレッション（レップ範囲の上限を全セットで達成したら負荷を 1 刻み上げ、
レップを下限に戻す）で「今日の目標」を計算し、入力欄に流し込んでいた。理屈は正しいが、
**達成できなかった日に必ず未達が表示される**作りになる。体調・睡眠・仕事の都合で届かない日は
必ず来るので、続ける妨げのほうが大きいと判断して外した。

いまは次のようになっている。

- 入力欄には**前回と同じ数字**が入っている。ゼロから打ち込ませないためだけの初期値で、
  目標の意味は持たない
- ✓ を付けると**前回との差**だけが出る（`+1レップ` / `±0` / `−1レップ`）。
  伸びたときだけ色が付き、落ちた日は無彩色で数字だけ出す
- まだ ✓ を付けていない行の下に、前回の同じセットが薄く出る。遡らせない
- ゲージや達成率のような「どこまで届いたか」の表示は持たない

種目カードの下にある「やり方と効く場所 / これまでの記録 / 推移 / この日のメモ」は
**節ごとに独立して開閉する**。1 つのまとまりにしていたときは、開いたあと閉じる場所が
カードの見出ししか無く、長い節を開くとその見出しが画面外に出て閉じられなかった。
いまは見出し自体がボタンなので、同じ場所を押せば閉じられる。開く前に件数が見えるので、
開くかどうかを決められる。

### 1.2 何を「前進」とみなして祝うか

記録を更新した瞬間に、画面中央で祝福が出る。条件は思いつきではなく、
過負荷の実装手段として挙げられているものに対応させた。

ACSM は漸進性過負荷の手段を複数挙げている（負荷・レップ数・セット数・ボリューム・
density・頻度など）。このアプリが実際に記録しているのは重量とレップ数、そこから出る
セット数とボリュームなので、判定はその 4 つに絞っている。休憩時間や可動域は
記録していないので判定できない（できないものを条件に混ぜない）。

4 つの手段にはそれぞれ、**1 セットで測る面**と**その日ぶんを合計して測る面**がある。
両方を見ないと拾えない前進があるので、8 つに分けてある（強い順）。

| 出す条件 | 対応する手段 | 判定 |
| --- | --- | --- |
| **最高到達点** | 負荷 | 推定 1RM（`重量 × (1 + レップ/30)`）が過去の最高を超えた |
| **重量更新** | 負荷 | 扱った重量そのものが過去最高を超えた（アシストは補助を減らした） |
| **レップ更新** | レップ数 | **同じ重量**での単一セットのレップが、その重量での過去最高を超えた |
| **レップ更新**（自重系） | レップ数 | 重さで測れない種目で、単一セットのレップが過去最高を超えた |
| **総レップ更新** | レップ数 | **同じ重量**での 1 日の合計レップが、その重量での過去最高を超えた |
| **セット数更新** | セット数 | その種目の実施セット数が過去最高を超えた |
| **種目の総量更新** | ボリューム | その種目の 1 日の総量が過去最高を超えた |
| **1日の総量更新** | ボリューム | セッション全体の総量が過去最高を超えた |

下 2 つ（**重量更新**と**総レップ更新**）は、単発のセットだけを見ていると
1 つも祝われない日があるために足した。

```
これまで  30kg × 10 + 30kg × 10 + 30kg × 8   （同じ重量で 計 28 レップ）
今日      30kg × 10 + 30kg × 10 + 30kg × 10  （同じ重量で 計 30 レップ）
```

単一セットの最高レップは 10 のままで、推定 1RM もセット数も動かない。だが同じ重さで
2 レップ多く挙げているので明確な前進で、**総レップ更新**がこれを拾う。**重量更新**も
同じ理由で、推定 1RM は重量とレップの積なので、重量を上げてレップを落とした日には動かない
——だが持てなかった重さを持ったことは負荷の前進そのものなので、別に数える。

重量とレップを**対等に**扱っているのは、8 週間の RCT で「重量を上げる群」と
「重量を固定してレップを伸ばす群」の筋肥大・筋力がほぼ同等だったため。つまり
「同じ重量で 1 レップ増えた」は「重量が 2.5kg 増えた」と同格の前進で、
前者だけ祝われないのは設計として間違っている。

逆に**総ボリュームは下位に置いている**。同じ研究は効果を「努力と実施セット数」に
帰属させ、volume load では説明していない。出しはするが、上の 2 つより順位を下げた。

出し方の決めごとが 5 つある。

- 1 回の ✓ で複数当たることは普通にあるので、**一番強いものを主役にして、残りを
  その下に 1 行ずつ添える**。片方しか映さないと「重量も上がって同じ重さでのレップも
  伸びた」日に何がどう動いたのかが分からない。添えるのは 3 つまで（それ以上並べると、
  次のセットに戻るまでが長くなる）
- **どの行にも増分を置く**（`+2 レップ` / `+2.5kg`）。到達した数字と前の記録の 2 つが
  出ていても、どれだけ進んだかはその場で引き算しないと出てこない。祝う場面で計算をさせない
- 同じ種類はそのセッションで 1 回だけ（3 セット全部で更新しても 1 回）
- 比較できる過去が無い項目は出さない。初日を「更新」と呼ばない
  （ただし到達点そのものは初回でも祝う）
- **1 セットに対して褒めるのは 1 回。** その ✓ で当たった種類は、上限で溢れたぶんも含めて
  全部「出した」ことにして覚える。そうしないと ✓ を外して入れ直すたびに次の順位の記録が
  出てくる（実際にそうなっていた）。この時点で当たっていない種類は覚えないので、
  あとのセットで本当に新しい記録が出たときはちゃんと祝われる

**✓ を外したときは何も出ない**（祝福は「実施済みにした瞬間」にだけ出る）。外した時点で
そのセットは集計から抜けるので、要約・カレンダー・推移はすべて計算し直される。
そのセットが始めた休憩タイマーも畳む（押し間違いで付いた ✓ を外したとき、意味のない
残り時間を数え続けないため）。別のセットが始めた休憩は消さない。

判定は `src/lib/records.ts` にあり、単体テストで固めてある。

> 出典: [ACSM: Ten Ways to Implement the Principle of Progressive Overload](https://journals.lww.com/acsm-healthfitness/fulltext/2022/03000/shareable_resource__ten_ways_to_implement_the.17.aspx) /
> [Progressive overload without progressing load? (load vs repetition progression RCT)](https://pmc.ncbi.nlm.nih.gov/articles/PMC9528903/)

### 1.3 停滞にだけは触れる

自己ベストから 3 セッション更新が無いと、種目カードを開いたときだけ小さく出る。
負荷を落として組み直す・角度やグリップを変える、という選択肢を置くだけで、
未達としては表示しない。

カレンダーの連続記録は**週単位**で数える。日単位だと休養日で必ず切れて、
休むことが罰になってしまう。

### 1.4 1 日の終わりに、一度だけまとめる

記録は触った時点で保存されるので、終わりを宣言する必要は仕組みの上では無い。
それでも面の一番下に**「今日を終える」**を置いているのは、やった分を一度だけまとめて
受け取る場所が要るから。セットごとの祝福は 1 回ぶんの前進しか映さないし、
上に出ている 3 つの数字は入力中ずっと出ているので、終わった実感には結びつかない。

押すと出るのは、その日の数字（セット・種目・総量）、**やったこと**（種目とその日の
重量・レップ）、**進んだこと**（何がどこまでどれだけ動いたか）、続いていること
（今週の回数・連続週・通算・前回比）と、**事実に基づく一言**。

数字だけの締めは、その日に何をやったのかを何も語らない。`60kg × 10 · 10 · 8` の
並びをそのまま置けば、あとから開いたときに他の画面へ行かずに中身を思い出せる。
同じ重量が続くところはまとめ、変わったところで区切るので、行の形がその日の組み立てになる。

一言は強い順に見て、最初に当てはまったものを出す。

| 出す条件 | 一言 |
| --- | --- |
| 記録が 2 つ以上動いた | 記録が N つ動いた日。 |
| 記録が 1 つ動いた | 今日、記録が動いた。 |
| 前回より総量が 5% 以上多い | 前回より総量が N% 多い。 |
| 4 週以上続いている | N 週続いている。 |
| 今週 2 回目以降 | 今週 N 回目。 |
| 2 週以上続いている | N 週続いている。 |
| 通算 2 日以上 | これで通算 N 日。 |
| （どれにも当たらない） | やった、が残った。 |

**「よく頑張った」のような、何をしても同じ文が出る褒め方はしない。** 毎回同じなら
次から読まれなくなるし、その日の中身と関係が無いので嘘に近い。逆に、**回数が少ない日を
責める文は 1 つも持っていない**——出るのは積み上がった側だけで、足りない側の欄は無い。

決めごとがいくつかある。

- **✓ が 1 つも無い日には出さない。** 何もしていない日に終わりのボタンがあると、
  押すこと自体が記録のように見える
- **記録更新は種目ごとに当たったものを全部拾う。** 祝福は 1 回ぶんの前進を一瞬映すもの
  なので一番強い 1 つでよかったが、締めは何がどう進んだのかを確かめる場所なので、
  重量も伸びてレップも伸びた日にその両方が残らないとまとめとして足りない。
  並ぶ数が増えても読めるのは、更新の一覧ではなく**やった種目の隣**に置いてあるから。
  種目ごとの判定なので、3 セットで同じ種類が 3 回並ぶことは無い。
  1 日の総量だけは種目に属さないので、種目ごとの判定から外して 1 回だけ見る
- **一言の「N つ」は更新の件数ではなく、動いた「もの」の数。** 種目 1 つで 3 種類
  当たっても 1 と数える。件数で言うと、重量を 2.5kg 上げただけの日が
  「記録が 4 つ動いた日。」になり、数が中身と合わなくなる
- **数字は 0 から数え上がる。** 止まった数字がいきなり出るより、積み上げた量として読める。
  `prefers-reduced-motion` では最初から最終値を置く。画面が描画されない状態
  （背面のタブなど）でも最後に必ず最終値を置く保険を掛けてある——演出が動かないのは
  構わないが、数字が違うのは困る
- **過ぎた日には「終える」を出さない。** もう終わっている日に終わりを宣言させても
  意味が無いので、まとめを開くだけの静かな操作にしてある（時刻も残さない）
- 押した時刻は `finishedAt` としてセッションに残す。記録そのものには一切効かない
  ——集計も祝福もこの値を見ない。効くのは画面だけ

判定は `src/lib/wrapup.ts` にあり、単体テストで固めてある。画面（`Wrapup.tsx`）は
出てきたものを並べるだけなので、「何をもって讃えるか」を変えるときに触るのは
あちらだけで済む。

### 1.5 今日の一枚

締めの画面から、その日を 1 枚の画像に組んで端末の共有シートに渡せる。

画面をそのまま撮ると上部バーもタブも入って何を見せたいのか伝わらないので、
その日を組み直した版面を作る。載せるのは一言・セット数・種目数・総量・部位・
**やった種目とその重量とレップ**・**進んだこと**（見出し・到達した数字・増分・前の記録）・
連続週。地は暗い側で固定してある——明るい地に赤 1 色だと SNS の中で沈む。

**幅は 1080 で固定、高さは中身で伸びる**（下限 1350 = 4:5）。以前は 1080×1350 の
固定版面だったが、種目とその重量・レップを載せるようになって、日によって行数が変わる。
行数に合わせて字を詰めると、種目が多い日だけ読めない 1 枚になる。字の大きさを保って
紙のほうを伸ばすほうが、どの日も同じ密度で読める。下限を 4:5 にしてあるのは
SNS でいちばん縦に大きく出る比だからで、種目が少ない日はこの比のまま。

高さが中身で決まるので、描く前に高さが要る。**同じ関数を測る回と描く回で 2 回**通し、
1 回目の戻り値で canvas の高さを決めてから 2 回目で描く（組み方を 2 箇所に書くと、
測った高さと描いた中身がずれる）。載せ切れない日のために、種目は 12・更新は 6 を上限にして、
溢れたぶんは「ほか N 種目」に畳む。

**見出しは挨拶ではなく事実のほう。**「お疲れ様でした」は自分に向けた労いなので、
他人が見る紙面に置いても意味を持たない。1 枚に載るのは「記録が 3 つ動いた日。」の側。

**外へ送るのは端末の共有シートに渡すところまで**で、このアプリはどこにも送らない
（オフラインで動くことが要件なので、そもそも送り先を持っていない）。共有シートが
無い環境では画像として保存する。

SVG を画像に変換する経路（`<img src="data:image/svg+xml">` → canvas）は取っていない。
端末ごとに字形が変わるうえ、Safari では汚染扱いで `toBlob` が落ちることがある。
canvas に直接描けば、依存も足さずどの端末でも同じ絵が出る（`src/lib/sharecard.ts`）。

### 1.6 サイクル——更新の単位はセッションではない

種目ごとにレップ範囲を持っている（多関節は狭く低め、単関節は高め。既定値は
プリセットが持ち、種目ごとに直せる）。ダブルプログレッションでは、範囲の上限を
全セットで達成したら負荷を 1 刻み上げ、レップは下限へ落ちる。つまり**進歩の単位は
セッションではなくサイクル**（同じ負荷でのひとまとまり）で、セッション同士を
並べると、上げた直後の日が必ず「後退」に見えてしまう。

そこで種目カードに、目標ではなく**現在地**を 1 行置いた（`src/lib/cycle.ts`）。

- `60kgで 3 回目 · 上限 8 レップ到達 2/3 セット` ——この負荷で何回やって、
  どこまで来たか。上限到達セット数がサイクル最多を更新したら「この負荷で最多」と添える
  （同じ重量でセットの中身が充ちていくことも前進なので、そこに名前を付けた）
- 全セットで上限に到達したら「**卒業**」。刻みから計算した次の負荷を**提示だけ**する。
  入力欄には入れない——上げるかどうか、いつ上げるかは本人が決める
- 卒業を決めた ✓ の瞬間には、**祝福のカード**が出る（`Graduation.tsx`）。器は記録更新の
  祝福と同じで、格は常に金。バーベルの線画にプレートが 1 枚降りてきて据わり、
  「これまで 75kg → 次 77.5kg」が横に並ぶ——達成と、次に進めることを文より先に絵で言う。
  アシストは逆にプレートが浮いて外れ（補助が減る）、自重のまま卒業したときは
  次のプレートを点線の輪郭で置いて「ここに足せる」ことだけ示す。
  同じ ✓ で記録更新も立ったときは、卒業のカードに小さく添えて 1 枚にまとめる
- その日に引き当てたカード（卒業・記録更新）は、**その日の記録のいちばん下の棚**に
  小さく並ぶ（`DayCards.tsx`）。押せば祝福のカードがもう一度開く——見返しなので
  自動では閉じない。祝福の演出用の印（sessionStorage）には頼らず記録から毎回
  引き直すので、過去の日を開いても当時のカードがそのまま並ぶ（`lib/cards.ts`）。
  1 枚も無い日は棚ごと出ない——0 枚の棚は未達の表示になってしまう
- 到達 0 セットの日は分数を出さない。`0/3` は今日の未達の表示になってしまう
  （1 章の原則。卒業も同じで、**成功したときにしか出ない判定**だから表示できる）
- セットごとの前回比も、負荷が上がっていればレップが落ちても赤（前進）にする。
  推定 1RM の引き算では「下がった」に見えるが、これはサイクルの起点であって後退ではない
- 自重種目は卒業したら「加重するか、難度を上げた種目へ」、アシストは補助を刻みぶん
  **減らす**方向へ。補助 0 まで来たら「補助なしでいける」

停滞もサイクルで見る。同じ負荷での 1 日の合計レップが 4 回続けてサイクル内の最高を
超えなかったら、「レップ範囲・セット数・種目のどれか **1 つだけ**変える」と促す
（全部変えると何が効いたか分からなくなる）。同じ数字を繰り返すのも停滞に含める
——自己ベスト基準の判定は、同じ数字を出し続ける限り「ベストに居る」と言うので、
卒業に近づいていないことを拾えない。

### 1.7 出席と復帰——切れない記録より、戻れた回数

いちばん効く変数は種目でも重量でもなく**ジムに行った回数**なので、頭打ちしない
指標を上に置く。記録タブの要約は 月の回数 · 総量 · **通算** · 週連続 · **復帰** の並びで、
通算は伸びが停滞している月も必ず増える。

連続記録（週単位）は前からあるが、切れた瞬間に 0 へ戻る指標で、切れたあとの行動を
映さない。定着を「途切れないこと」ではなく「**途切れても戻れること**」と定義して、
空いた週のあとに戻った回数を**復帰**として別に数える（1 週空けても 3 週空けても、
戻れば 1 増える。1 回もサボっていない人には出ない——0 を見せない）。

復帰した週の最初の日は、締めの一言でも記録更新より先に「空いた週から、戻ってきた。」
と言う。その日に言うべきことは数字ではない。

### 1.8 バランス——偏りは重量より先に見た目に出る

目的はボディメイクなので、偏りの検出を 3 軸で持つ：**部位**・**押す/引く**・
**前面/背面**（`src/lib/balance.ts`）。部位だけでは「肩はやっているが前だけ」
「押す種目ばかり」を拾えない。分類は主働筋から引く——押す/引くは本来種目の性質だが、
主働筋が決まればほぼ決まる（大胸筋が主働で引く種目は無い）。上腕は面と動作が
逆になる（二頭＝前面だが引く、三頭＝後面だが押す）ので、2 軸は独立に持つ。

記録タブに直近 4 週のセット数で出す。4 週なのは、週 2 回の種目で 8 回ぶん
——1 回サボっても比率が壊れず、昔のメニューの偏りも引きずらない長さ。

- 部位は 6 行全部出す。**0 セットの部位も行ごと出す**——やっていないことは、
  行が無いと気づけない
- 押す/引くと前面/背面は 1 本の棒。境目の位置が比率そのもの
- 片側がもう片側の 2 倍を超えたときだけ、少ない側を事実として言う
  （計 12 セット未満では言わない。数セットの週に比率を言っても意味が無い）。
  **直せとは言わない**——弱点部位に寄せている期間は正しい運用なので、
  気づけることと責められることを分ける
- 体幹と、分類できない自作種目は比率の分母に入れない。分からないものを
  どちらかに数えると、検出そのものが信用できなくなる

棒は全部無彩色。赤は「前進」の軸に取ってあるので、偏りの表示には使わない。

## 2. 重さを設定しない種目（自重・アシスト）

ジムのマシンには**重さを設定しない**ものがある。ローマンチェアのバックエクステンション、
チェアのレッグレイズ、アシストチンニング。どれも「重量の欄に何を入れるのか」が
その場で分からなくなる種目で、実際に迷った。

種目ごとに「負荷のかけ方」を 3 択で持たせて、**入力欄の意味そのものを切り替える**。

| かけ方 | 入力する数字 | 欄の見え方 | 進める向き |
| --- | --- | --- | --- |
| 重量 | 持ち上げる重量 | `62.5` `kg` | 上げる |
| 自重 | 自重に**足した**ぶんだけ | `自重` `+kg` | レップで伸ばす |
| アシスト | マシンに設定する補助重量 | `27.5` `kg` | **下げる** |

### 自重（重さを設定しない種目）

- **欄は空欄のままでいい。** 触る前から `—` ではなく **`自重`** と出ていて、
  単位は `kg` ではなく **`+kg`**。裸の `kg` だと、体重を入れるのか総重量を入れるのか
  決まらない。「自重 +kg」と並んでいれば、入れるのが**足したぶん**だと形で分かる
- **初めてやる日にだけ 1 行出す。**「自重のままなら重さは空欄のまま ✓。ベルトやプレートで
  加重した日だけ +kg に入れる」。2 回目以降は同じ位置に前回の記録が出るので消える
  ——迷うのは初回だけなので、案内も初回だけにする
- **記録の書き方も揃える。** 前回の行は `自重×12 / 加重 5×10`、前回との差は `加重 +2.5kg`。
  裸の kg で残すと、あとで読み返したときに持ち上げた重量と区別が付かない
- 伸びは**レップで測る**。1 日の総量（kg）にも足さない——単位の違うものを合算すると、
  その日の総量が意味を持たなくなる
- 加重を始めた種目の到達点は「推定 1RM」と呼ばない。**「到達点」**と呼ぶ。出しているのは
  自重に足したぶんの到達点で、自重そのものは数に入っていない——数えていないものを
  名前で数えたことにしない（バックエクステンションで `推定 1RM 6.7kg` と出ていた）
- プリセットに**バックエクステンション**と**レッグレイズ**を入れてある。どちらも
  「自重で回数を伸ばし、足りなくなったら加重する」種目

### アシスト（数字を下げるほど負荷が上がる）

アシストチンニングのようなマシンは、設定した補助重量ぶん体が軽くなる。
実際に引いているのは **体重 − 補助重量**で、進める向きも普通の種目と逆になる。

- セット行の下に `実際に引く重さ 42.3kg（体重 69.8 − 補助 27.5）` を常に出す。暗算させない
- 「一番きついセット」は**補助が最小**のセット。上限レップ到達で補助を 1 刻み下げる
- ボリュームと推定 1RM は実効負荷で計算する
- 達否は「補助が目標以下」で判定する（`27.5 ≤ 27.5` なら達成）
- 前回との上下比較も向きを揃える（補助が少ないほうが上）

**体重**は今日の画面に入力欄がある。設定に 1 つ持つのではなくセッションに持たせているので、
過去の記録を後から計算し直しても当時の体重で出る。その日に未記録なら直近の値を引き継ぐ。
体重が一度も入っていないアシスト種目は、実効負荷が出せないのでレップ数で測る方に落ちる
（進め方の判定はマシンの数字だけで決まるので、体重が無くても機能する）。

## 3. 種目とその説明

初期種目は 42。プリセットは `src/lib/presets.ts` の 1 箇所にあり、
それぞれ「やり方 / 効く筋肉 / コツ」を持つ。

- **やり方**: 思い出せる程度の 1〜2 文。ジムで長文は読まない
- **効く筋肉**: 前面・背面の図で主働筋を赤、補助を薄い赤で塗る（`BodyMap`）。
  写実的な解剖図にしていないのは、小さく描くとかえって読めないため
- **コツ**: そこに効かせるために意識すること 2〜3 個

これらは読み物で、書き換えるものではない。自分の体とジムに固有のこと（ラックの段数、
シート位置、自分だけ引っかかる点）は種目の **tips** に書く。tips はカードの一番上に常に出る。

**入っていないもの**: 有酸素運動（ランニング）と「その他」。このアプリのデータ模型は
重量 × レップで、時間・距離を持っていない。無理に入れると記録の合算が意味を失うので、
必要になったら型から足す。

### 記録を別の種目にまとめる

プリセットに無い種目は自分で作ることになる。あとから同じ種目がプリセットに入ると、
一覧に同じものが 2 つ並び、しかも**自分で作った側には説明が付かない**——説明は
プリセットの id に紐付いているため。移す手段が無いと、それまでの記録を捨てるか、
説明を諦めるかの二択になる。

種目の設定に「記録を別の種目にまとめる」を置いた（`src/lib/merge.ts`）。

- 移すのは**記録だけ**。まとめ先の設定（名前・レップの目安・刻み・コツ）はそのまま
- 同じ日に両方の記録がある日は、**セットを後ろに継ぎ足す**。順番を入れ替えない
- メモは両方あれば改行でつなぐ。片方を捨てない
- 元の種目に触っていない日は**そのまま返す**。セッション配列の同一性で結果を使い回している
  計算（`query.ts`）があるので、無関係な日を作り直すとその手当てが全部無駄になる
- 元の種目は消さず**非表示にする**。削除は「無い」ことを表す更新を作れないので、
  last-write-wins では次の同期で戻ってくる
- 取り消せないので、押す前に「4 日ぶん・12 セットの記録が移る」と数を出す。
  同じ名前の種目が並ぶ場面のための操作なので、選択肢には負荷のかけ方を添える
  （`レッグレイズ（重量）` / `レッグレイズ（自重）`）

**まとめなくても済む場合がある。** 0kg で回数だけ記録していた種目は、
**負荷のかけ方を「自重」に変えるだけ**で `0kg × 15` が `15・15・14 レップ` になり、
欄も `自重` `+kg` に変わる。記録は 1 件も動かない。まとめる必要があるのは、
プリセットの説明（やり方・効く筋肉・コツ）まで欲しいときだけ。

## 3.5 体重

体重はトレーニングをしない日にも入れるものなので、**今日の画面の一番上**と、
**専用のタブ**の 2 か所から入力できる。種目カードの下にあると、開いて下まで
スクロールしないと入力に届かない。

体重タブには折れ線と日々の差分、それに**この先の予想**が出る。縦軸は 0 から始めない
（体重の変化幅は全体の数 % なので、0 起点にすると線が平らになって何も読み取れない）。
横軸は日付の実距離で置く（記録が空いた期間が詰まって見えないように）。

**目標体重は持たない。** 今日の画面から目標を外したのと同じ理由で、達していない状態が
毎日表示されると続かない。出すのは実測と差分と、その実測を延ばした線だけ（下の 3.6）。
予想が近づいていく「落ち着き先」は身長から出す BMI の帯で、**目指す値ではなく、
そこへ近づくほど線が寝るという形でしか効かない**。

体重はセッションに持たせているので、アシスト種目の実効負荷を後から計算し直しても
当時の体重で出る。

### 保存する条件と「やった日」の条件は別

紛らわしいので分けて名前を付けてある（`src/lib/types.ts`）。

- `worthStoring` — 保存するか。**体重を含める。** 体重しか無い日を保存しないと、
  休養日に入れた数字がそのまま消える（実際にそうなっていた）
- `hasRecord` — カレンダーに「やった日」として出すか。**体重を含めない。**
  体重だけの日を塗ると、毎日入れるほどカレンダーが埋まって動いた日が分からなくなる

同じ理由で、Claude に渡す体重の推移も「やった日」からではなく全部の記録から作る。
やった日だけに絞ると、休養日に付けた体重が落ちて推移がほとんど残らない。

## 3.6 成長の予想

体重にも種目の到達点にも、**記録を延ばした線**を添えてある。体重タブの折れ線と、
種目カードの「推移」の節の 2 か所。判定は `src/lib/forecast.ts` に閉じ込めてあり、
画面（`TrendChart.tsx`）は出てきたものを描くだけ。

### 予想は目標ではない

このアプリは目標を出さない（1.1）。予想はその決めごとを崩さない。出しているのは
**過去の記録を延ばした線**であって、届くべき線ではない。外しても何も起きないし、
外したことを言う表示は 1 つも持っていない。下を向いた線もそのまま出す。

**締め・祝福・今日の一枚には一切出てこない。** あれは「その日やったこと」を置く場所なので、
起きていないことを同じ紙面に混ぜない。

### 直線では伸ばさない

傾きをそのまま伸ばすと、体重はいつか 0 に届き、種目の重量はいくらでも上がる。
どちらも起こらない。**伸びは必ず鈍る**ので、そこを式に入れてある。

効かせる場所は 2 つ。

- **速さの上限。** 観測した傾きがこれを超えていたら、予想はこの速さで引く。
  ひと月だけ出た速さを、3 か月続く前提に使わない
- **落ち着き先。** そこへ近づくほど緩む曲線にする。式は
  `v(t) = limit − (limit − v0)·e^(−kt)` で、`k` は今日の傾きから決める。
  だから**線は実測の傾きちょうどで始まって、先へ行くほど寝る**（継ぎ目に折れが出ない）

どちらも **`forecast.ts` は受け取るだけ**で、中身は呼ぶ側が決める。体重と種目で
現実的な速さも落ち着き先もまるで違うので、片方の都合をもう片方に持ち込まないため。

#### 体重

| | 値 | 根拠 |
| --- | --- | --- |
| 落ち着き先（減る向き） | **BMI 20** の体重（174cm なら 60.6kg） | 標準（BMI 22）だと絞っている途中の人には手前すぎてすぐ線が寝る。痩せの境（18.5）まで下げると、そこを目指せる線に見えてしまう |
| 落ち着き先（増える向き） | **BMI 25** の体重（同 75.7kg） | 標準の上限 |
| 速さ（減る向き） | 週に体重の **1%** | これより速い減量は、続けても除脂肪体重ごと落ちていく速さ |
| 速さ（増える向き） | 週に体重の **0.5%** | 増量は速いほど脂肪の割合が増えるので、上限は減量より厳しく取る |

身長は**設定に持たせた**（`profile.ts`、既定 174cm）。**localStorage に置いて、
記録にも同期にも載せていない**——毎日変わる値ではないし、そのために保存と
バックアップと突き合わせの規則を 1 つ増やすほうが高くつく。

向きによって上限が変わるので、**予想は 2 度通す**。1 度目で向きだけ取り、
2 度目でその向きの上限を渡して引き直す（純関数なので 2 度呼んでも同じ答えになる）。

#### 種目

落ち着き先は**体重比**で持つ（`presets.ts` の `bodyweightCap`）。扱える重量は体格に
比例するので、70kg の人と 90kg の人に同じ上限を置いても意味が無い。ベンチプレス 1.5 倍、
スクワット 2.0 倍、デッドリフト 2.5 倍——といった、**鍛え続けた人が届くあたり**を
プリセットごとに 1 つずつ置いてある。

数字はざっくりで構わない。**越えたら効かなくなる**（そのときは実測の傾きがそのまま線になる）
ので、低く見積もりすぎても線が早く寝るだけで、記録は何も変わらない。

持たせていないものが 3 つある。**自重種目**（測っているのがレップか加重したぶんなので、
体重比の上限が意味を持たない）、**自分で足した種目**（何の種目か分からないものに上限を
置かない）、**体重が未記録の日**（掛ける相手がいない）。どれも落ち着き先なしで予想する。

速さの上限は**その種目を何回やったか**で決める。伸びは訓練歴とともに必ず鈍るが、
歴そのものは記録していないので、回数で代わりに測る（週 2〜3 回なら 12 回で約 1 か月）。

| その種目の記録 | 月あたりの上限 |
| --- | --- |
| 〜12 回 | 直近の到達点の 3% |
| 13〜40 回 | 1.5% |
| 41 回〜 | 0.7% |

### 実測と予想は、色ではなく線で分ける

| | 描き方 |
| --- | --- |
| 実測 | 赤の実線＋薄い塗り |
| 予想 | **赤の点線**と、ぶれの幅を表す薄い帯 |
| 今日 | 縦の点線。ここから右は起きていない |
| 落ち着き先 | 横の細い点線（枠に入るときだけ） |
| 着地点 | 中を抜いた丸（実測の点と別のものだと形で分かる） |

最初は予想を無彩色にしていた。赤は「記録を更新した」「前回より伸びた」「今日である」
——実際に起きたことの合図に取ってあるので（7 のデザイン方針 2）、まだ起きていない
ものには渡さない、という理屈だった。

だが実際に並べると、予想だけ灰色に沈んで**同じ推移の続きに見えない**。別の何かが横に
置いてあるように読める。予想は同じ 1 本の推移の先の話なので、色は続けて、
**点線という切れ方で「まだ無い」と言う**ほうが素直だった。点線・帯・今日の縦線の
3 つが揃っていれば、赤のままでも実測と取り違えようがない。

破線ではなく**点線**にしてあるのは、破線が「線が続いている」ようにも読めるため。
点が並んでいるだけの列は、どう見ても実線の代わりではない。

落ち着き先の横線は、**越えられない壁ではない**ので格子より少し濃い程度に留めてある。
帯もそこで止めない——越えられないと言い切れるものを、このアプリは持っていない。

### どう出しているか

**半減期つきの加重最小二乗**。直近の点ほど重く見る（半減期 42 日 = 6 週）。減量期のあとに
増量期が来れば線の向きは変わるべきで、3 か月前の点が今の傾きを決めてはいけない。

**点で言い切らない。** 予想には必ず幅（`±`）が付く。中身は最小二乗の予測区間そのもので、
「記録そのものの散らばり」＋「平均の不確かさ」＋「平均から離れた距離」の 3 つ。
3 つめがあるので、**先へ行くほど帯が広がる**。値だけを大きく置くと当たる約束に見えるので、
数字のすぐ隣に幅を並べてある。

出さない条件を 4 つ持っている。足りない状態で線を引くと、1 点のぶれがそのまま
「この調子なら」になってしまう。

| 出さない条件 | 理由 |
| --- | --- |
| 点が 4 つ未満 | 3 点では 1 点のぶれが傾きをそのまま決める |
| 記録の幅が 14 日未満 | 1 週間の記録から先を言わない |
| 観測した期間の 2 倍より先 | 上限つきの線になったので直線のときよりは伸ばせるが、3 週間の記録から 1 年先を出せるようにはならない |
| 最後の記録が古い | 途切れたところから先を語らない（伸ばせる長さを使い切ったら止まる） |

出ないときは黙らず、**あと何があれば出るのか**だけ 1 行で出す
（`あと 2 回ぶん記録すると予想が出る`）。「予想できません」には情報が無い。

**先は 90 日まで**。直線で伸ばしていたころは 30 日で止めていた——それ以上先は
「毎月同じだけ上がり続ける」という、起こらないことの絵になっていたため。いまは線が
寝るので、「どのへんで落ち着くのか」が読めるところまで出す。

### 言い方

```
この調子なら 90日後  66.7 kg   幅 ±0.2 kg   直近から −2.7 kg
落ち着き先の目安 60.6 kg · BMI 20
```

- **横ばいだけ言い方を変える**（`横ばいが続けば`）。動いていない線に「この調子なら」と
  付けると、進んでいるように読める
- **差は直近の実測と比べる。** 線の上の今日の値と比べるほうが式としては揃うが、
  読む側が知っているのは最後に測った数字のほう
- **落ち着き先には根拠を添える**（`BMI 20` / `体重比 2×`）。数字だけ置くと、
  どこから出てきた値なのか分からない。効いていない日はこの行ごと出さない
- 「横ばい」の線引きは対象で変える。体重は 30 日で 0.3kg（日々のぶれと区別が付かない）、
  種目は**直近の 1%**（60kg の種目の 0.5kg は横ばいだが、20kg の種目では前進）

### 体重タブでは、見ている期間が予想の元になる

上の `1か月 / 3か月 / 全期間` は折れ線の窓であると同時に、**予想の元にする期間**でもある。
全期間の傾きで 1 か月の窓に線を引くと、目の前の点と線がずれて見える。切り替えたのに
何も変わらないのも同じくらい困るので、窓と予想を一致させてある。

そのため 1 か月を見ているときは観測期間も 1 か月で、外挿の上限もそのぶん短くなる
（`90日後` ではなく `57日後` になったりする）。短くなったこと自体が、
どれだけの記録から言っているのかの表示になっている。

## 4. 「記録をつけられるのは自分だけ」をどう満たしているか

**境界は「推測できない鍵を知っているか」1 つ。**

記録は Firestore の `vaults/{鍵から導いた ID}/...` の下にある。`vaults` 自体の一覧は
Security Rules で許可していないので、鍵を知らないと自分の領域に到達できない。
鍵は 20 文字（100 ビット）で、総当たりは現実的でない。

### 鍵をビルドに埋め込むことはできない

GitHub Pages が配信するバンドルは誰でも読める。ビルド時に埋め込んだ値は、
GitHub Secrets 経由であっても**バンドルに入った時点で秘密ではなくなる**。
だから鍵は「端末ごとに 1 回入力して localStorage に置く」しかない。入力は 1 回だけなので、
長くても困らない（起動時に `navigator.storage.persist()` を呼んでいるので、
許可されればストレージが追い出されず入力し直しも起きない）。

初回に鍵を発行し、別の端末では同じ鍵を入れると同じ記録が開く。設定画面から鍵を表示・
コピーできる。短い語を鍵にすることもできるが、その場合は同期先が総当たりで
見つかりうる旨を画面に出す。

### 鍵を作らずに使える

**鍵が要るのは同期先を決めるためなので、同期しないなら鍵は要らない。** 入口に
「鍵を使わずにこの端末だけで使う」を置いてある。選ぶと記録はこの端末の IndexedDB
だけに残り、機能は何も減らない（同期だけが無効になる）。

**この選択は片道ではない。** 記録は鍵と結びついていないので、あとから設定画面で鍵を
作れば、それまでの記録ごと同期が始まる（最初の同期がすべてを送る）。すでに他の端末で
使っている鍵を入れて、その領域に合流することもできる（同じ日の記録は `updatedAt` の
新しい方が残る）。取り返しがつくので、入口では確認を挟まず 1 タップで進める。

入り方は localStorage の 2 つの印で表す。`overload:vault-key`（鍵）と
`overload:local-only`（鍵なしで使うと決めた印）で、**両方が同時に立つことはない**
（`storeKey` は鍵なしの印を落とし、`clearEntry` は両方消す）。両方立つと入り方が
決まらず、鍵を消したのに入口が出ない状態になる。「決めていない」（どちらも無い）と
「鍵なしで使うと決めた」を区別しているのは、区別しないと鍵を作らないと決めた人に
毎回入口を出すことになるため。

### Google サインインをやめた理由

「自分のメールアドレスだけ許可する」は Rules 側は 1 行で書けるが、**サインインの経路が
GitHub Pages では成立しない**。Firebase の認証は `authDomain`（`<project>.firebaseapp.com`）と
別オリジンの iframe を使い、この仕組みは Safari 16.1+ / Firefox 109+ のサードパーティ
ストレージ分割で動かない。公式の回避策は「Firebase Hosting でホストする」
「`signInWithPopup` を使う」「`/__/auth/` をリバースプロキシする」の 3 つで、
Pages はプロキシを置けない。残るポップアップは、iOS のホーム画面に追加した PWA で
開かない／`window.opener` が null で結果を返せないことが報告されている。

鍵方式なら対話的なログインが 1 度も要らず、どの環境でも同じように動く。引き換えに、
**鍵（と同期先 ID）が漏れればその領域は読めてしまう**。個人のトレーニング記録に対しては
妥当な取引と判断した。メール制限をやるなら、ホスティングを Firebase Hosting へ移すのが
現実的な道になる（アプリのオリジンが認証ハンドラと同一になり、リダイレクト方式が通る）。

> 出典: [Firebase: Best practices for signInWithRedirect](https://firebase.google.com/docs/auth/web/redirect-best-practices) /
> [PocketBase: OAuth2 login flow is not supported on installed PWAs on iOS](https://github.com/pocketbase/pocketbase/discussions/2429)

## 5. 同期（Firestore）

記録の正はいつでもこの端末の IndexedDB。同期はその写しを Firestore と突き合わせるだけで、
**オフラインで開けることを SDK の読み込みや同期の成否に依存させていない**。
同期が一度も成功しなくても、アプリの機能は何も減らない。

規則は `updatedAt` の大きい方を採る（last-write-wins）。1 人が数台で使う前提なので、
同じ日の同じ種目を 2 台で同時に編集することは実際には起きない。CRDT を持ち込むより、
規則が 1 行で説明できるほうが後で自分が読める。

送信待ちの列（outbox）は持っていない。オフライン中に送れなかった変更も、次の同期で
「ローカルの updatedAt が大きい」ことから同じ結論が出るので、列を別に持つと
二重管理になるだけで得るものが無い。走らせる契機は 4 つ（起動時・オンラインに戻ったとき・
画面が前面に戻ったとき・ローカルを触って 4 秒後）。定期実行はしない。
圏外では試行そのものを見送る（送ろうとして失敗させると、実際には何も失われていないのに
「同期できていない」と表示されるため）。

差分だけを取る仕組みは持たないので、1 回の同期で「セッション数 + 種目数」ぶんの
読み取りが発生する。画面の前面復帰ごとに走らせると無料枠（1 日 5 万読み取り）を
無駄に削るので、**自動で走る同期には 60 秒の最小間隔**を入れてある。設定画面の
「いま同期する」はこの間隔を無視する。

Firebase SDK は動的 import で、`firestore/lite` を使っている（SDK 側の永続キャッシュは
使わない。ローカルの保存は自前の IndexedDB が持っているので二重に持つ意味がない）。

**種目は物理削除しない。** 削除は「無い」ことを表す更新を作れないので、
last-write-wins では次の同期で消したはずの種目が戻ってくる。`archived` の
切り替えなら普通の更新として伝わる。セッションを空にしたときは、空のセッションを
リモートに送って「消した印」にしている（取り込み側で落とすと両側が一致する）。

> **保存する条件と「消した印」の条件は必ず一致させる。** `isTombstone` は
> `worthStoring` の裏返しとして定義してある。別々に書いていたときは、
> 体重だけ付けた休養日が「消した印」と見なされ、**同期先の端末で体重が消えていた**。
> 保存する対象を増やすときは、片方だけ直すと記録が失われる。

### セットアップ

**同期が要らないなら丸ごと飛ばせる。** 入口で「鍵を使わずにこの端末だけで使う」を
選べば設定なしで使える。あとから鍵を作れば、それまでの記録ごと同期が始まる。

1. [Firebase Console](https://console.firebase.google.com/) で Firestore を有効化する
   （news-curator で作ったプロジェクトに相乗りしてよい）
2. **Authentication → Sign-in method → 匿名** を有効にする
3. プロジェクト設定 → アプリを追加 → ウェブアプリを登録し、`apiKey` / `projectId` / `appId` を控える
4. リポジトリの **Settings → Secrets and variables → Actions → Variables** に登録する

   | Name | Value |
   | --- | --- |
   | `VITE_FIREBASE_PUBLIC_API_KEY` | Firebase の apiKey |
   | `VITE_FIREBASE_PUBLIC_PROJECT_ID` | Firebase の projectId |
   | `VITE_FIREBASE_PUBLIC_APP_ID` | Firebase の appId |

   `PUBLIC` が付いているのは名前のとおり秘密にしなくてよい値だから。Firebase の
   apiKey はアクセス制御に使われず（制御は Security Rules 側）、ビルド済み JS に
   そのまま入って誰でも見られる前提の値。Secrets ではなく Variables に置くのは
   実態と合わせるため。

5. Firestore → ルール を貼って公開する

   **設定画面の「Security Rules をコピー」から、同期先 ID が埋まった文面をそのまま
   取れる**ので、それを貼るのが早い。中身はこの形になっている。

   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       match /vaults/{vault}/{document=**} {
         allow read, write: if request.auth != null && vault == '<自分の同期先 ID>';
       }
     }
   }
   ```

   **ID の固定は省略できない。** 匿名サインインは誰でも通せるので、`request.auth != null`
   だけを条件にすると、公開サイトを開いた人が自分の領域を作ってこのプロジェクトに
   書き込める。他人の記録は読めない（別の ID なので到達できない）が、容量と無料枠は
   消費され、あなたの同期が止まりうる。ID を固定すれば領域そのものを作れなくなる
   （拒否された要求は読み書きの課金対象にならない）。

   同期先 ID は鍵の SHA-256 で、**鍵と同じくらい秘密にする**（ID を知っている人は
   匿名サインインを通せば読み書きできる）。Security Rules はクライアントから読めないので、
   ここに書いても漏れない。

未設定でもアプリは動く。その場合は設定画面に同期が無効である旨が出て、
記録はこの端末だけに残る。無効の理由は「設定が入っていない」と「鍵を作っていない」で
書き分けている（`Sync.off`）——足すものが違うので、同じ文面にすると次の一手が分からない。

## 6. 記録を Claude に渡して相談する

「記録」画面の「記録を渡して相談する」を押すと、期間ぶんの記録・種目の設定・コツ・メモ・
体重の推移を積んだ状態で Claude の新規チャットが開く。期間は 4 週間 / 12 週間 / 全期間。

依頼文は**ボディメイクを目的にした語りかけ**を求める形にしてある。数字を並べた分析
レポートを返されると読まなくなって形骸化するので、次のように頼んでいる。

1. 続いていること・変わったことを、記録から具体的に 2〜3 個
2. 見た目の観点で次に効く一手を 1〜2 個だけ（多いと動けない）
3. バランスの偏りを 1 つだけ
4. 次にジムへ行くときに思い出せる短い言葉

API は使わない。プロンプトをクエリに載せた URL を開くだけなので、鍵も費用もかからず、
ログインしている本人のアカウントでそのまま会話が始まる。iOS / Android ではこの URL が
Claude アプリの Universal Link になっているのでアプリが開く。デスクトップアプリは
claude.ai のリンクの受け皿にできないので、押したときに同じ内容をクリップボードにも
入れている（アプリに貼れば続けられる）。

URL に載せられる長さには上限がある。日本語は 1 文字が `%E3%81%82` の 9 文字になるので、
種目名とメモが効く。上限を超える場合は優先度の低い節（メモ → コツ → 古い種目）から
落とすが、**クリップボードには常に全文が入る**ので、貼れば失われない。

## 7. デザインの方針

コンセプトは「洗練された上質な肉体を作るためのトレーニングプロデュース」。
`src/styles.css` の冒頭にも同じことを書いてある。

1. **完全な無彩色 + 赤 1 色。** ベージュや焙煎色のような色味を地に置くと、それ自体が
   主張して記録の数字より先に目に入る。地は無彩色に徹して、色は赤だけに任せる
2. **赤は面ではなく信号として使う。** ヘッダを赤で塗る作りは目立つが安くなる。
   「記録を更新した」「前回より伸びた」「今日である」だけに赤を割り当て、
   それ以外は無彩色。右下（実際には左下）の追加ボタンのような、まだ何もしていない
   操作には一番強い色を渡さない（地と反転した無彩色にしている）
3. **書体はゴシック 1 系統だけ。** 明朝を混ぜると和の情緒が出て、淡々と数字を置く道具という
   性格から外れる。字間の演出も最小に留めた。外部フォントは読み込まない
   （オフラインで動くことと、初回表示の速さを崩さないため）
4. **文字で説明せず記号で示す。** タブ・メモ・増減・前回・閉じるといった繰り返し出る
   ラベルはアイコンに置き換えた（`src/components/Icon.tsx`）。逆に記録の数字とコツの文章は
   文字のまま残す（記号にすると意味が伝わらない）。部位も色の点ではなく漢字 1 文字で示し、
   カレンダーは角丸タイルではなく罫線の格子にした
5. **達成の色に緑を使わない。** 赤と緑の信号色はどのフィットネスアプリにもある。
   赤が入る = 前進した、無彩色 = 変化なし、という 1 軸に寄せる

祝福の演出は、細い線が外へ走って消えるだけにしてある。紙吹雪のような賑やかな演出は
この画面の静けさから浮く。`prefers-reduced-motion` では線を出さない。

### 細部の決めごと

見た目の印象より、指と目に効く部分を実測して決めている。

- **色の役割を 2 つに分けた。** `--faint` は飾りと記号だけに使い、文字を載せない
  （以前は 2.3:1 しか出ておらず、前回の値や件数が沈んでいた）。塗りの赤と
  小さな赤文字も分けてある（`--accent` / `--accent-text`）。塗りの赤のまま小文字にすると
  暗い地で 3.8:1 しか出ず、明るくすると今度は白抜きの文字が弱くなるため
- **当たり判定は見た目を変えずに広げる。** メモの丸（28px）や閉じる（36px）は、
  透明な当たり判定を外へ伸ばして 44px 相当にしてある。セット行の高さは 44px。
  数値欄の幅は「62.5」が収まることを優先しているので、稼ぐのは高さ側
- **数字の欄は触ると空になる。** 前回の数字を消してから打つことがほとんどなので、
  選び直す手間を省く。元の数字は影（プレースホルダ）で残し、**打たずに離れたら
  元に戻す**——ここで最小値に落とすと、隣を触るつもりの一撫でや変換の取り消しで
  記録が消える。0 にしたいときは 0 と打つ（どの欄も `min` は 0）
- **0 は影にも残さない。** 0 のまま置いてある欄（初めてやる種目の重量、まだ入れていない
  体重）は「まだ入っていない」という意味しか持たないので、消す価値のある数字ではない。
  それを影として残すと、消したはずの 0 がまだ居るように見えて、実際に「毎回 0 を消してから
  打つ」使われ方になっていた。いまは 0 の欄は触る前から `—` で、触れば完全に空になる。
  打たずに離れれば 0 のまま戻る
- **欄から欄へ送れる。** 端末のキーボードの確定キーが「次へ」になっていて、押すと
  重量 → レップ → 次のセットの重量、とカードの中を順に渡り歩く。1 セットぶんを入れる
  あいだ、画面に指を戻さなくていい。並びは DOM の順そのものなので、セットを増やしても
  行き先の表を別に持たなくて済む
- **✓ を押すと指に返る。** ジムでは画面を見ずに押すことがあるので、ごく短い振動を返す
  （入った = 10ms、記録が動いた = 間を置いて 2 発）。`navigator.vibrate` の無い端末では
  何も起きない。鳴らない前提で作ってあるので、これが効くかどうかで操作の可否は変わらないし、
  触覚を当てにした文言も置かない
- **入力の見せ方は 2 通りだけ。** カードの中（記録に添える文章）は**下線だけ**、
  シートの中（種目の設定）は**枠付き**。カードという枠の中にさらに枠を置くと、
  四角が入れ子になって記録そのものが埋もれる
- **記号と文字で同じことを言わない。** 部位の漢字 1 文字は、名前が出ない場所
  （種目カードの見出し）専用。一覧やシートの見出しは文字があるので記号を置かない
- **同じ重さのボタンを並べない。** 鍵を消す操作は「表示する」と並べず、
  文字だけの静かな操作にして一段挟む。押し間違いで同期先に戻れなくなるため
- **取り消せない操作は「何が失われるか」を出して一段挟む。** 種目を外すときの問いかけは
  「よろしいですか」ではなく「2 セットの記録と 1 件のメモが消える」と数を出す。
  焦点は最初から「やめる」に置き、危ない側は必ず右に置く。Escape と地の部分でも閉じる
- **同じ操作の入口を 2 つ並べない。** 追加ボタンは、末尾の普通のボタンが見え始めた時点で
  浮いている方を引っこめる。判定は末尾のボタン自身を見張る（`IntersectionObserver`）ので、
  記録が増えて高さが変わっても表示とずれない。スクロールが要らない短い日は、
  最初から末尾のボタンだけになる
- **推移の測り方は履歴で決める。** 今日の記録で決めると、まだ ✓ を 1 つも付けていない
  朝のあいだは常に「重さで測れていない」になり、見出しが「最高レップ」に化けて、
  そこに推定 1RM の数字がレップとして出る（`直近 200.66666 レップ`）。
  推移が見ているのは履歴なので、測り方も履歴から決める
- **キーボードで辿ったときだけ枠を出す**（`:focus-visible`）。ブラウザ既定の枠は
  この配色では見えないことがある
- **安全域は外枠で 1 回だけ持つ。** `viewport-fit=cover` を指定しているので、
  これが無いとホーム画面から起動したときに上部バーが時計やノッチの下へ潜る
- 触った瞬間の反応を少しだけ遅らせている（✓ は 130ms、節の展開は 280ms）。
  即座に切り替わると機械的に見え、長いと待たされる
- **✓ は線が引かれる。** 塗りが変わるだけだと、押した結果が色でしか返ってこない。
  線が引かれる動きを足すと、書き込んだ操作として読める（外したときは逆再生しない
  ——取り消しは記録ではないので、静かに消えるだけでいい）
- **まだ ✓ の付いていない行の数字は一段落としてある。** 入っているのは前回と同じ数字で、
  まだ今日の記録ではない。同じ濃さで置くと、並べただけの行が全部「やったこと」に見える。
  ✓ を付けた行だけが本文の濃さになるので、カードを上から下へ埋めていく手応えが出る
- **面の一番下に置いたボタンは、浮いているものを自分で避ける。** 追加ボタンと休憩タイマーは
  画面に貼り付いているので、スクロールしきった位置でその下に潜る（実際に休憩中は
  「種目を追加」の字が半分隠れていた）。避ける高さを `--float-clear` として数で持ち、
  末尾の塊がそのぶん空ける。面全体ではなく塊が持つのは、浮くものが何も無いタブで
  底に空白が残らないようにするため
- **寸法・色・丸み・時間はすべて token にしてある。** 角は 4 段（6 / 9 / 13 / 18px）で、
  入れ子になったときに輪郭が平行に見えるよう「外側 = 内側 + 内側の余白」で決めている。
  字は 9 段だが隣り合う段の差は 1〜2px——この画面のほとんどが「数字と、その数字が
  何なのかを言う小さな字」の 2 つでできているので、段を大きく開けると説明の字が本文に
  見えてしまう
- **面の上端に 1px だけ光を入れている**（`--sheen`）。暗い地では境界線だけだと面が
  「切り抜かれた穴」に見えて、押せる場所に見えない。線として見えない濃さで止めてある
- **終わりのボタンも赤で塗らない。** 赤は「前進した」の合図に取ってあるので、押す前の
  操作には渡さない。地と反転した無彩色にしてあり（浮いている追加ボタンと同じ扱い）、
  赤が出るのは押したあとのまとめの中だけ

### 長い弧——通算・初日から・更新の年表

1 セット・1 日の前進は祝福と締めが手厚く扱っているが、「何ヶ月でどれだけ変わったか」を
受け取る場所が無かった。それを 3 つ足した（`src/lib/milestones.ts`）。
どれも**過去の事実の言い換え**で、目標ではない——未達が出うる形
（週◯回のノルマ、達成率、ゲージ）はここにも作らない。

- **通算の積み上げ。** 記録タブの月の数字の下に
  「これまでに 27 日 · 154.7 t 積み上げた」の 1 行。**絶対に減らない数字**で、
  休んでも下がらない——週単位の連続記録と同じ性質を、数字の側で持つ。
  10t を超えたら t で言う（412,530kg は桁を数えないと読めないが、412.5t は
  読んだ瞬間に量として伝わる）
- **初日から直近まで。** 種目カードの「これまでの記録」と種目シートの記録の面に
  「初日 8週間前 70kg × 8 → 75kg × 10」の 1 行。目標と違って外れようがない
  ——比べる相手が未来ではなく過去だから。伸びていれば矢印と今の値に赤が入り、
  落ちていれば無彩色の数字のまま出る（隠しはしない。セットの差分と同じ扱い）
- **更新の年表。** 記録タブに、記録が動いた日**だけ**が並ぶ。祝福と同じ判定
  （`records.ts`）を過去に流し直すので、当時祝われたものと食い違わない。
  動かなかった日は行ごと無い——足りない側の欄を作らない。種目を足しただけの初日は
  「更新」ではないので入れない。押せばその日に飛ぶ

### 種目一覧と、種目の 2 面

種目一覧の各行の右に、**到達点の推移の小さな線**（スパークライン）を添えた。
軸も目盛も無く、上がっているか・止まっているか・落ちているかの形だけを見せる。

- 線は**無彩色**。推移の折れ線の実線は赤だが、一覧では全行に付くので、ここまで
  赤にすると信号としての赤が薄まる（赤の総面積が小さいほど 1 つ 1 つが効く）。
  赤が入るのは**直近が自己ベストの行の終点**だけ——いま前進の途中にある種目が
  一覧の中で光る
- 点は直近の 20 日ぶんまで。72px に何十点も入れると線が毛羽立って形が消える

種目を開いたシートは**「設定」と「記録」の 2 面**に分けた。設定は従来の編集項目、
記録はスパークラインを開いた先——同じ推移を数字と一緒に読める面で、
通算（回数・自己ベスト・その種目の積み上げ）、推移の折れ線と予想、初日から直近まで、
これまでの記録の一覧が縦に並ぶ。折れ線の組み立て（測り方・落ち着き先・伸びの上限）は
種目カードの推移の節と同じ決めごとに従う——別の式を使うと、カードとシートで違う線が出る。

- 現在地は**赤い下線**で示す。塗りのボタンにすると保存より強く見えるし、
  下のタブバーの現在地と同じ言い方なので、覚えることが増えない
- 新しい種目にはまだ記録が無いので、面を分けずに設定だけ出す
- 開くたびに設定の面へ戻す。記録を見たまま別の種目を開くと、前の種目の記録面が
  一瞬出て、どの種目を開いたのか分からなくなる

### 何も無い日の面

「今日」の面は、種目を 1 つも足していないあいだ**説明の 1 行しか無かった**。
記録が中身のすべてなので、無い日は面のほとんどが空白のまま残り、開いた瞬間に
「まだ始まっていない」ではなく「壊れている」に見えていた。

空白を埋めるための飾りは足さない。置いたのは**プレートを 1 枚も挿していないバー**
1 つで、これは飾りではなく**その日の状態そのもの**——まだ何も積んでいない、という
1 対 1 の対応がある。種目を足せば消えるので、消えることにも意味がある。

- **色は無彩色のまま。** 赤は「前進した」の合図に取ってあるので、まだ何もしていない
  面には渡さない。字を載せない飾りなので、一番弱い `--faint` を使える
- **動かない。** 最初はバーが左から右へ引かれる演出を付けていたが、外した。
  この面は 1 日に何度も通る場所で、通るたびに動くものは 2 回目から邪魔にしかならない
- **柱はバーより上へ出さない。** 受けのフックを描くと線がバーを横切り、1 本の棒に
  見えなくなる。ローレット（握る位置の刻み）も入れていない——この大きさでは
  カラーと見分けが付かず、線の多い図になるだけでバーには見えない
- **字は 3 段。**「今日の記録がありません」→「最終履歴：昨日（脚）」→
  「種目を追加すると…」の順で、大きさも濃さ（`--fg` / `--fg-dim` / `--muted`）も
  1 段ずつ落としてある。開いた瞬間に知りたいのは**状態**のほうで、操作の説明は
  2 度目以降は読まれない。1 段目は絵より上、日付の見出しと同じ大きさ——この面で
  いちばん強いのは「何日を見ているか」と「そこに何があるか」の 2 つで、
  片方だけ大きいと、もう片方が見出しの添え物に見える
- **「今日」と言い切らない。** 過ぎた日・先の日を開いていることは普通にあるので、
  そのときは「この日の記録がありません」に変わる。日付そのものは見出しに出ているので、
  ここで入れ替えるのは「今日 / この日」だけ
- **2 段目に置くのは事実だけ。**「今日も頑張ろう」のような、何日空けても同じ文になる
  呼びかけは置かない（締めの一言と同じ理由。1.4）。判定は ✓ の数で、メモだけ書いた日は
  最終履歴に数えない——開けた日数が実際と合わなくなる。「昨日」はいま見ている日
  から数えるので、8 月 29 日を開けば 8 月 27 日が「おととい」になる

### 広い画面（Web）

**スマホで詰めた寸法は動かさない。** 実機で決めた当たり判定と行の高さを、画面が
広いという理由で崩さない。足すのは 2 段だけで、どちらも `@media (min-width: …)`
の中にしかない。

| 幅 | 変わること |
| --- | --- |
| 〜60rem（960px） | スマホと完全に同じ。タブレットの縦（768px）もここ——指で使う幅では下の帯のほうが近い |
| 60rem〜 | 行き先が下の帯から**左の筋**へ移る（記号に字が付いて縦に積む）。セットの行が**1 行に畳まれる**。シートが中央の札になる。設定の横幅いっぱいのボタンが字の分の幅に縮む |
| 72rem〜（1152px） | 面が**2 列**に割れる。今日＝種目｜日付と要点、記録＝カレンダー｜最近の記録、体重＝折れ線｜一覧 |

考えたことをいくつか。

- **2 列を 60rem から始めない。** そこで割ると本文の列が 23rem しか残らず、
  **スマホより狭くなる**。広くしたのに窮屈になるのでは逆行になる
- **入力欄は伸ばさない。** 幅が余ったからといって数字の欄を広げても読みやすく
  ならない。「32.5」の右に空白が広がるだけなので、余りは数字の**意味**
  （実効負荷・前回との差）を横に並べるほうに使う
- **右の列は貼り付けて残す**（`position: sticky`）。種目を送っているあいだも
  日付と要点とメモが視界にあるので、いま何日のどこを見ているのか確かめに戻らない
- **カレンダー側は広げない。** 日の枠は正方形なので、列を広げると 1 マスが巨大に
  なって「月を一目で見る」道具でなくなる。余った幅は右の一覧に回す
- **設定は 40rem で止める。** 1 行が 60〜70 字を超えると読み返す位置を見失う
- **段の数を幅ごとに決めない。** セットの行は幅を固定しない要素を並べてあるので、
  入りきる画面では 1 行に、狭ければ自分で折り返す。前回との差を省略記号で
  切るより、行が増えるほうがまし
- 束ねるためだけに足した `div`（`.shell` / `.session-aside` など）は狭い画面では
  `display: contents` で**無かったことになる**。だからこれらを足しても
  スマホの見た目は 1px も変わらない
- タブの名前は常に DOM にあり、狭い画面では見えなくするだけ（読み上げには残る）。
  `display: none` だと押せるものの名前が消える。記号側に名前を持たせないのは、
  広い画面で字と記号が同じことを 2 回言わないため

**タブは横スワイプで移動でき、指に追従して面がスライドする。** 隣の面は指を動かし始めた
時点で用意し、離した時点で移動量（画面幅の 26%）か速さで切り替えるか戻すかを決める。
最初のわずかな動きで縦横どちらの操作かを判定し、縦と決まった指では何もしない
（`touch-action: pan-y` で縦は素の挙動に任せ、横だけ JS が扱う）。入力欄・シート・数値欄の
上から始まった操作は無視する。端では動かさない——動かないことで端だと分かる。

**画面の骨格は app-shell 型。** 文書そのものはスクロールせず、面の中だけがスクロールする。
そのためタブバーはスクロールに関係なく常に同じ位置にいる。上部の帯は面の中で sticky。

**拡大操作は止めてある。** viewport の `user-scalable=no` に加えて、iOS Safari は
これを無視することがあるので Safari 独自の gesture イベントも潰し、二度叩きの拡大は
`touch-action: manipulation` で止めている。入力欄に触れたときの自動拡大も起きなくなる。

**種目の追加ボタンは左下に固定してある。** セット行の ✓ は右端に並ぶので、右下に置くと
スクロール位置によって ✓ の上に重なる。✓ は 1 セッションに何十回も押す操作で、種目の追加は
数回。頻度の低い操作を遠い側に置いて、頻度の高い操作を塞がないほうを取った。

**日付は 1 行に収める。** 日付・曜日・「今日」を縦に積むと視線が縦に動く。曜日だけ
カレンダーの慣習に合わせて**土は水色、日は赤**にしてある（祝日は扱わない）。
この 2 色が「無彩色 + 赤」の唯一の例外。休日の区別は色以外に置き換えが効かない
（文字を足すと画面が説明で埋まる）ので、意味のある色として通した。使うのは曜日の
1 文字だけに限っている。

**上部の帯は面の中で固定して追従する。** 体重はトレーニングをしない日にも入れるものなので、
スクロールした先からでも届く位置に置いた。

「体重」の字は数値欄のすぐ左に、間を詰めて置いてある。離すと右上の数字が何なのか
結びつかない（実際に分からないという指摘を受けて直した）。直近の値は**今日まだ入れていない
ときだけ**、「前回」と日付を添えて出す。素の数字だけでは何なのか伝わらないし、今日ぶんを
入れたあとは同じ数字が 2 つ並ぶだけになるので消える。

アイコンは**バーを担いだ V**。上の横棒がバーベル、下が V で、V は肩幅から腰へ絞る
逆三角形のシルエット。バーが V の肩幅より少し外へ出ているのは、実際に担いだときの
見え方に合わせたもの。

**定型の三角をやめた理由。** 最初は三角形（＋水準を表す線）で組んでいたが、三角形は
輪郭が一般的すぎて何のしるしにも見えない。中に逆三角形を抜く案も試したが、
外形が定型の三角のままで、抜いた窓は小さいサイズで消える。バーと V の 2 要素にすると
固有の輪郭になり、間の余白も意味を持つ（担いでいる、という関係が余白で読める）。
18px でも形が保つことを実測で確かめてから決めた。

V は**ワードマークの V と同じ字形**を使っている。印と字で同じことを言い、内側の谷の
深さも同じ比率（高さの約 60%）に揃えてある。器具そのものの絵にしなかったのは、
道具の説明になってしまい「produce する」立場が出ないため。

角はすべて丸めてある。塗りと同じ色の線を重ねて（`stroke-linejoin: round`）落としている。
数学どおりの鋭角は小さく描くと潰れて濁るため。

`scripts/make-icons.mjs` が図形から PNG を直接生成する（SVG 変換ツールは環境によって
入っていないので、依存を増やさずどこでも同じ絵が出るようにした）。`npm run icons` で作り直せる。

## 8. オフライン

- **アプリ本体**: Service Worker が dist の中身を全部プリキャッシュする。2 回目以降は
  圏外でもホーム画面から起動できる
- **記録**: IndexedDB。書き込みにネットワークは一切関わらない。触った時点で保存される
  （保存ボタンは無い）
- **更新**: 新しい版が来ても自動で再読み込みしない。セットの途中で画面が入れ替わるのが
  一番困るので、バナーを出して押すまで待つ

Workbox は入れていない。やることが「dist を全部プリキャッシュする」だけなので、
生成された `dist/sw.js` をそのまま読んで理解できる状態のほうがよい。
ハッシュ付きファイル名は事前に分からないため、`vite.config.ts` のプラグインが
ビルド後に `public/sw.js` のプレースホルダを実際の一覧へ置き換えている。

IndexedDB が開けない/固まっている環境では、4 秒で諦めてメモリだけで動かし、
設定画面に「保存できていない」と出す。`indexedDB.open` は success も error も blocked も
飛ばないまま黙り込むことがあり、待ち続けると起動画面のまま何も出ない状態になるため。

## 8.5 サンプルの記録

**空の画面では何も分からない。** 初めて開いた人には記録がゼロ件しか無く、
このアプリの主題（前回との差・記録更新・推移・締め）はどれも過去の記録が無いと出ない。
人に見せるときも、自分の記録を開いて見せることになる。

そこで、**作りものの 9 週間**を持たせてある。

### 入り方は 3 つ

| どこから | 誰のため |
| --- | --- |
| 入口の「まずは中身を見る — サンプルの記録で試す」 | リンクを初めて開いた人 |
| URL に `#demo` を足す（`https://…/overload/#demo`） | 人に渡すとき・開発中に確かめるとき |
| 設定 →「サンプルの記録を開く」 | すでに使っている人が誰かに見せるとき |

`#demo` は**保存された入り方より強い**。自分の記録が入っている端末でも、その URL なら
サンプルが開く。抜けるときは URL からも `#demo` を落とすので、開き直しても戻ってこない。

### 戻る

面の一番上に帯が出ていて、押せば入口（または自分の記録）に戻る。確認は挟まない
——サンプルの中では何をしても失うものが無い。

### 決めごと

- **保存先に一切触らない。** サンプル中のストアはメモリだけで動く（`StoreProvider` に
  seed を渡すと IndexedDB を開きもしない）。実測で、サンプルを見たあとの端末に
  データベースが 1 つも作られていないことを確かめてある
- **入り方が変わったらストアごと作り直す。** React は同じ位置の同じ部品を使い回すので、
  key を分けないとサンプルの中身が残り、しかも次の書き込みが本物の保存先へ向かう
  （実際にそうなった）。念のためストア側でも、メモリだけで動くかどうかをマウント時に固定している
- **決定的に作る。** 乱数の種を固定してあるので、同じ日に開けば誰でも同じ画面になる。
  紹介するときに「この画面のここ」と言える
- **今日を基準に作る。**「3 週間前」が常に 3 週間前になるので、いつ開いても
  カレンダー・推移・停滞判定が生きている。作った日で固定すると、時間が経つほど
  「昔の記録しか無いアプリ」に見えてしまう
- **今日は途中まで。** 1 セット目に ✓ が付いていて残りが空いている。しかも今日は重量を
  1 段上げた日にしてあるので、見ている人がそのまま ✓ を押せば**必ず記録更新が出て**、
  祝福・休憩タイマー・「今日を終える」・まとめ・今日の一枚まで一通り体験できる
- **全機能に実物を 1 つずつ当ててある。** 重量種目の漸進、アシスト（補助を下げる進み方）、
  自重種目が加重に移る瞬間、体重の推移、休養日、メモ、機材設定、締め済みの日

中身は `src/lib/demo.ts`。「id がプリセットに実在する」「✓ を押せば記録更新が出る」
「前回の数字が引ける」といった、サンプルが**サンプルとして成立しているか**を
テストで固めてある（画面を開かないと壊れたことに気づけないため）。

## 9. 使い方

```bash
npm install
npm run dev        # http://localhost:5180/overload/
npm test           # 計算部分の単体テスト
npm run typecheck
npm run build && npm run preview   # Service Worker の確認はこちら
npm run icons      # アイコンを再生成する
```

dev サーバーでは Service Worker を登録しない（`public/sw.js` が置換前のままなので）。

### GitHub Pages に出す

1. リポジトリを push する
2. **Settings → Pages → Build and deployment → Source** を **GitHub Actions** にする
3. main に push すると `https://<ユーザー名>.github.io/<リポジトリ名>/` に出る

`base` はリポジトリ名から決まる（`BASE_PATH` で上書きできる）。同期を使うなら
「5. 同期」のセットアップも行う。

> GitHub Pages を private リポジトリで使うには有料プランが必要。無料プランなら
> public リポジトリにする。記録はリポジトリに入らず、鍵もバンドルに入らないので、
> public でも記録が漏れることはない。

### ホーム画面に追加する

iPhone なら Safari で開いて共有 → ホーム画面に追加。以降は単体のアプリとして起動し、
圏外でも開ける。iOS では Safari と PWA で保存領域が別なので、**記録を貯めるのは
どちらか片方に決める**（同期を有効にしていれば、どちらでも同じ記録が開く）。

## 10. バックアップ

同期していても、Firebase の外に自分で持っておける形が 1 つあると戻せる。
設定画面から 4 通り出せる。

| 手段 | 用途 |
| --- | --- |
| ファイルに書き出す | PC で保存する |
| 共有 | iPhone からファイルアプリ等へ送る |
| JSON をコピー | どこかに貼る |
| GitHub のエディタで開く | リポジトリの `data/` にコミットして履歴に残す |

GitHub に置く方は、書き込み権限のあるトークンをブラウザに持たせない。ログイン済みの
GitHub の Web エディタへ本文ごと飛ばすので、編集できるかどうかはリポジトリの権限で決まる。

読み込みは 1 箇所でも形が合わなければ全体を拒否し、どこが合わないかを出す。
壊れた JSON を部分的に取り込むと、どこまで戻ったのか分からなくなるため。

## 11. 構成

```
src/lib/          UI から独立した計算とデータ層（ここだけテストがある）
```

日付を `Date` に入れて戻す往復はしない。タイムゾーンで 1 日ずれる事故が起きるので、
`'YYYY-MM-DD'` 文字列のまま計算する（`calendar.ts` にテストがある）。

並べ替えと体重の引き当ては、セッション配列の同一性で結果を使い回している（`query.ts`）。
種目カードごとに全セッションを並べ替え、その中で 1 日ずつ体重を線形探索していたため、
記録が増えると種目数 × 日数の二乗で効いていた。配列は保存のたびに作り直されるので、
中身が変われば勝手に作り直される。

`presets.ts` は手書きのデータが 40 件あるので、整合性を機械で見ている
（id の重複・レップ範囲の逆転・説明の欠落・主働筋と補助筋の重複など）。
綴り間違いは型が捕まえるが、これらは型では通ってしまう。

保存済みデータの読み出しは必ず `migrate.ts` を通す。項目を後から足したとき、
`set.note ?? ''` のような防御を各所に散らすと必ずどこかで漏れるので、
入口を 1 箇所にして以降は全項目が揃っている前提で書いている。

## 12. v0.4 に入っていないもの

- **同じ日の同じ種目を 2 台で同時に編集したときの解決**。last-write-wins なので
  後に保存した側が残る（1 人で使う前提として割り切っている）
- 有酸素運動（時間・距離の記録）
- **目標設定**。一度入れて外した。戻すなら「達成できなかった日のフォロー」を先に設計する
  （3.6 の予想は目標ではない。届くべき線ではなく、実測を延ばした線を出しているだけで、
  落ち着き先も「そこへ近づくほど線が寝る」という形でしか効かない）
- 休憩時間・可動域・頻度の記録（過負荷の手段だが、記録していないので祝福の判定にも使えない）
- 体組成（体脂肪率など）。身長だけは予想の落ち着き先を出すために設定に持っている
- RPE・セットの種類（アップ / メイン / ドロップ）の区別
- 種目の並び替え（今は「最近やった順 → プリセットの並び」で自動）
- 休憩タイマーの通知音。バックグラウンド通知は iOS の PWA では当てにならないので、
  鳴る前提の機能にしていない（画面上のカウントアップだけ）
