# OVERLOAD

洗練された上質な肉体を作るための、トレーニングプロデュース PWA。自分専用。

目的はボディビルや競技ではなく**ボディメイク**。見た目の質が上がることが成功で、
扱う重量はそのための手段として扱う。ただし手段は正確に管理する——というのがこのアプリの立場。

- **目標を出さない。** 入力欄には前回と同じ数字が入っているだけ。上げても下げてもただの記録として残る
- **前進があったときだけ祝う。** 記録を更新した瞬間にアニメーションが出る（条件は下に文献つきで書いた）
- 体重は毎日つける前提で画面の一番上。別タブで折れ線が見られる
- 種目ごとに**やり方・効く筋肉の図・一般的なコツ**と、**自分用の機材設定メモ**を持つ
- メモは**セットごと / その日のその種目 / その日全体**の 3 段階
- **アシストマシン**（数字を下げるほど負荷が上がる）を専用の扱いで入力できる
- 圏外でも開けて操作できる。記録は Firestore にも同期され、端末を失っても残る
- 記録をまとめて Claude に渡し、続けるための助言をもらえる
- サーバー費用 0 円（GitHub Pages + Firestore の無料枠）

## 1. 目標を出さず、前進だけを祝う

### 1.1 なぜ目標をやめたか

以前はダブルプログレッション（レップ範囲の上限を全セットで達成したら負荷を 1 刻み上げ、
レップを下限に戻す）で「今日の目標」を計算し、入力欄に流し込んでいた。理屈は正しいが、
**達成できなかった日に必ず未達が表示される**作りになる。体調・睡眠・仕事の都合で届かない日は
必ず来るので、続ける妨げのほうが大きいと判断して外した。

いまは次のようになっている。

- 入力欄には**前回と同じ数字**が入っている。ゼロから打ち込ませないためだけの初期値で、
  目標の意味は持たない
- ✓ を付けると**前回との差**だけが出る（`+1レップ` / `±0` / `−1レップ`）。
  伸びたときだけ色が付き、落ちた日は無彩色で数字だけ出す
- まだ ✓ を付けていない行の下に、前回の同じセットが薄く出る。遡らせない
- ゲージや達成率のような「どこまで届いたか」の表示は持たない

種目カードの下にある「やり方と効く場所 / これまでの記録 / 推移 / この日のメモ」は
**節ごとに独立して開閉する**。1 つのまとまりにしていたときは、開いたあと閉じる場所が
カードの見出ししか無く、長い節を開くとその見出しが画面外に出て閉じられなかった。
いまは見出し自体がボタンなので、同じ場所を押せば閉じられる。開く前に件数が見えるので、
開くかどうかを決められる。

### 1.2 何を「前進」とみなして祝うか

記録を更新した瞬間に、画面中央で祝福が出る。条件は思いつきではなく、
過負荷の実装手段として挙げられているものに対応させた。

ACSM は漸進性過負荷の手段を複数挙げている（負荷・レップ数・セット数・ボリューム・
density・頻度など）。このアプリが実際に記録しているのは重量とレップ数、そこから出る
セット数とボリュームなので、判定はその 4 つに絞っている。休憩時間や可動域は
記録していないので判定できない（できないものを条件に混ぜない）。

| 出す条件 | 対応する手段 | 判定 |
| --- | --- | --- |
| **最高到達点** | 負荷 | 推定 1RM（`重量 × (1 + レップ/30)`）が過去の最高を超えた |
| **レップ更新** | レップ数 | **同じ重量**での単一セットのレップが、その重量での過去最高を超えた |
| **レップ更新**（自重系） | レップ数 | 重さで測れない種目で、単一セットのレップが過去最高を超えた |
| **セット数更新** | セット数 | その種目の実施セット数が過去最高を超えた |
| **種目の総量更新** | ボリューム | その種目の 1 日の総量が過去最高を超えた |
| **1日の総量更新** | ボリューム | セッション全体の総量が過去最高を超えた |

重量とレップを**対等に**扱っているのは、8 週間の RCT で「重量を上げる群」と
「重量を固定してレップを伸ばす群」の筋肥大・筋力がほぼ同等だったため。つまり
「同じ重量で 1 レップ増えた」は「重量が 2.5kg 増えた」と同格の前進で、
前者だけ祝われないのは設計として間違っている。

逆に**総ボリュームは下位に置いている**。同じ研究は効果を「努力と実施セット数」に
帰属させ、volume load では説明していない。出しはするが、上の 2 つより順位を下げた。

出し方の決めごとが 4 つある。

- 1 回の ✓ で複数当たることは普通にあるので、**一番強いものだけ**を出す
- 同じ種類はそのセッションで 1 回だけ（3 セット全部で更新しても 1 回）
- 比較できる過去が無い項目は出さない。初日を「更新」と呼ばない
  （ただし到達点そのものは初回でも祝う）
- **1 セットに対して褒めるのは 1 回。** 表示するのは一番強い 1 つだが、その ✓ で
  当たった種類は全部「出した」ことにして覚える。そうしないと ✓ を外して入れ直すたびに
  次の順位の記録が出てくる（実際にそうなっていた）。この時点で当たっていない種類は
  覚えないので、あとのセットで本当に新しい記録が出たときはちゃんと祝われる

**✓ を外したときは何も出ない**（祝福は「実施済みにした瞬間」にだけ出る）。外した時点で
そのセットは集計から抜けるので、要約・カレンダー・推移はすべて計算し直される。
そのセットが始めた休憩タイマーも畳む（押し間違いで付いた ✓ を外したとき、意味のない
残り時間を数え続けないため）。別のセットが始めた休憩は消さない。

判定は `src/lib/records.ts` にあり、単体テストで固めてある。

> 出典: [ACSM: Ten Ways to Implement the Principle of Progressive Overload](https://journals.lww.com/acsm-healthfitness/fulltext/2022/03000/shareable_resource__ten_ways_to_implement_the.17.aspx) /
> [Progressive overload without progressing load? (load vs repetition progression RCT)](https://pmc.ncbi.nlm.nih.gov/articles/PMC9528903/)

### 1.3 停滞にだけは触れる

自己ベストから 3 セッション更新が無いと、種目カードを開いたときだけ小さく出る。
負荷を落として組み直す・角度やグリップを変える、という選択肢を置くだけで、
未達としては表示しない。

カレンダーの連続記録は**週単位**で数える。日単位だと休養日で必ず切れて、
休むことが罰になってしまう。

## 2. アシストマシン（数字を下げるほど負荷が上がる種目）

アシストチンニングのようなマシンは、設定した補助重量ぶん体が軽くなる。
実際に引いているのは **体重 − 補助重量**で、進める向きも普通の種目と逆になる。

種目ごとに「負荷のかけ方」を 3 択で持たせてある。

| かけ方 | 入力する数字 | 進める向き |
| --- | --- | --- |
| 重量 | 持ち上げる重量 | 上げる |
| 自重 | 加重があればその重量 | レップで伸ばす |
| アシスト | マシンに設定する補助重量 | **下げる** |

アシスト種目では次のように扱う。

- セット行の下に `実際に引く重さ 42.3kg（体重 69.8 − 補助 27.5）` を常に出す。暗算させない
- 「一番きついセット」は**補助が最小**のセット。上限レップ到達で補助を 1 刻み下げる
- ボリュームと推定 1RM は実効負荷で計算する
- 達否は「補助が目標以下」で判定する（`27.5 ≤ 27.5` なら達成）
- 前回との上下比較も向きを揃える（補助が少ないほうが上）

**体重**は今日の画面に入力欄がある。設定に 1 つ持つのではなくセッションに持たせているので、
過去の記録を後から計算し直しても当時の体重で出る。その日に未記録なら直近の値を引き継ぐ。
体重が一度も入っていないアシスト種目は、実効負荷が出せないのでレップ数で測る方に落ちる
（進め方の判定はマシンの数字だけで決まるので、体重が無くても機能する）。

## 3. 種目とその説明

初期種目は 40。プリセットは `src/lib/presets.ts` の 1 箇所にあり、
それぞれ「やり方 / 効く筋肉 / コツ」を持つ。

- **やり方**: 思い出せる程度の 1〜2 文。ジムで長文は読まない
- **効く筋肉**: 前面・背面の図で主働筋を赤、補助を薄い赤で塗る（`BodyMap`）。
  写実的な解剖図にしていないのは、小さく描くとかえって読めないため
- **コツ**: そこに効かせるために意識すること 2〜3 個

これらは読み物で、書き換えるものではない。自分の体とジムに固有のこと（ラックの段数、
シート位置、自分だけ引っかかる点）は種目の **tips** に書く。tips はカードの一番上に常に出る。

**入っていないもの**: 有酸素運動（ランニング）と「その他」。このアプリのデータ模型は
重量 × レップで、時間・距離を持っていない。無理に入れると記録の合算が意味を失うので、
必要になったら型から足す。

## 3.5 体重

体重はトレーニングをしない日にも入れるものなので、**今日の画面の一番上**と、
**専用のタブ**の 2 か所から入力できる。種目カードの下にあると、開いて下まで
スクロールしないと入力に届かない。

体重タブには折れ線と日々の差分が出る。縦軸は 0 から始めない（体重の変化幅は全体の
数 % なので、0 起点にすると線が平らになって何も読み取れない）。横軸は日付の実距離で
置く（記録が空いた期間が詰まって見えないように）。

**目標体重は持たない。** 今日の画面から目標を外したのと同じ理由で、達していない状態が
毎日表示されると続かない。出すのは実測と差分だけ。

体重はセッションに持たせているので、アシスト種目の実効負荷を後から計算し直しても
当時の体重で出る。

### 保存する条件と「やった日」の条件は別

紛らわしいので分けて名前を付けてある（`src/lib/types.ts`）。

- `worthStoring` — 保存するか。**体重を含める。** 体重しか無い日を保存しないと、
  休養日に入れた数字がそのまま消える（実際にそうなっていた）
- `hasRecord` — カレンダーに「やった日」として出すか。**体重を含めない。**
  体重だけの日を塗ると、毎日入れるほどカレンダーが埋まって動いた日が分からなくなる

同じ理由で、Claude に渡す体重の推移も「やった日」からではなく全部の記録から作る。
やった日だけに絞ると、休養日に付けた体重が落ちて推移がほとんど残らない。

## 4. 「記録をつけられるのは自分だけ」をどう満たしているか

**境界は「推測できない鍵を知っているか」1 つ。**

記録は Firestore の `vaults/{鍵から導いた ID}/...` の下にある。`vaults` 自体の一覧は
Security Rules で許可していないので、鍵を知らないと自分の領域に到達できない。
鍵は 20 文字（100 ビット）で、総当たりは現実的でない。

### 鍵をビルドに埋め込むことはできない

GitHub Pages が配信するバンドルは誰でも読める。ビルド時に埋め込んだ値は、
GitHub Secrets 経由であっても**バンドルに入った時点で秘密ではなくなる**。
だから鍵は「端末ごとに 1 回入力して localStorage に置く」しかない。入力は 1 回だけなので、
長くても困らない（起動時に `navigator.storage.persist()` を呼んでいるので、
許可されればストレージが追い出されず入力し直しも起きない）。

初回に鍵を発行し、別の端末では同じ鍵を入れると同じ記録が開く。設定画面から鍵を表示・
コピーできる。短い語を鍵にすることもできるが、その場合は同期先が総当たりで
見つかりうる旨を画面に出す。

### 鍵を作らずに使える

**鍵が要るのは同期先を決めるためなので、同期しないなら鍵は要らない。** 入口に
「鍵を使わずにこの端末だけで使う」を置いてある。選ぶと記録はこの端末の IndexedDB
だけに残り、機能は何も減らない（同期だけが無効になる）。

**この選択は片道ではない。** 記録は鍵と結びついていないので、あとから設定画面で鍵を
作れば、それまでの記録ごと同期が始まる（最初の同期がすべてを送る）。すでに他の端末で
使っている鍵を入れて、その領域に合流することもできる（同じ日の記録は `updatedAt` の
新しい方が残る）。取り返しがつくので、入口では確認を挟まず 1 タップで進める。

入り方は localStorage の 2 つの印で表す。`overload:vault-key`（鍵）と
`overload:local-only`（鍵なしで使うと決めた印）で、**両方が同時に立つことはない**
（`storeKey` は鍵なしの印を落とし、`clearEntry` は両方消す）。両方立つと入り方が
決まらず、鍵を消したのに入口が出ない状態になる。「決めていない」（どちらも無い）と
「鍵なしで使うと決めた」を区別しているのは、区別しないと鍵を作らないと決めた人に
毎回入口を出すことになるため。

### Google サインインをやめた理由

「自分のメールアドレスだけ許可する」は Rules 側は 1 行で書けるが、**サインインの経路が
GitHub Pages では成立しない**。Firebase の認証は `authDomain`（`<project>.firebaseapp.com`）と
別オリジンの iframe を使い、この仕組みは Safari 16.1+ / Firefox 109+ のサードパーティ
ストレージ分割で動かない。公式の回避策は「Firebase Hosting でホストする」
「`signInWithPopup` を使う」「`/__/auth/` をリバースプロキシする」の 3 つで、
Pages はプロキシを置けない。残るポップアップは、iOS のホーム画面に追加した PWA で
開かない／`window.opener` が null で結果を返せないことが報告されている。

鍵方式なら対話的なログインが 1 度も要らず、どの環境でも同じように動く。引き換えに、
**鍵（と同期先 ID）が漏れればその領域は読めてしまう**。個人のトレーニング記録に対しては
妥当な取引と判断した。メール制限をやるなら、ホスティングを Firebase Hosting へ移すのが
現実的な道になる（アプリのオリジンが認証ハンドラと同一になり、リダイレクト方式が通る）。

> 出典: [Firebase: Best practices for signInWithRedirect](https://firebase.google.com/docs/auth/web/redirect-best-practices) /
> [PocketBase: OAuth2 login flow is not supported on installed PWAs on iOS](https://github.com/pocketbase/pocketbase/discussions/2429)

## 5. 同期（Firestore）

記録の正はいつでもこの端末の IndexedDB。同期はその写しを Firestore と突き合わせるだけで、
**オフラインで開けることを SDK の読み込みや同期の成否に依存させていない**。
同期が一度も成功しなくても、アプリの機能は何も減らない。

規則は `updatedAt` の大きい方を採る（last-write-wins）。1 人が数台で使う前提なので、
同じ日の同じ種目を 2 台で同時に編集することは実際には起きない。CRDT を持ち込むより、
規則が 1 行で説明できるほうが後で自分が読める。

送信待ちの列（outbox）は持っていない。オフライン中に送れなかった変更も、次の同期で
「ローカルの updatedAt が大きい」ことから同じ結論が出るので、列を別に持つと
二重管理になるだけで得るものが無い。走らせる契機は 4 つ（起動時・オンラインに戻ったとき・
画面が前面に戻ったとき・ローカルを触って 4 秒後）。定期実行はしない。
圏外では試行そのものを見送る（送ろうとして失敗させると、実際には何も失われていないのに
「同期できていない」と表示されるため）。

差分だけを取る仕組みは持たないので、1 回の同期で「セッション数 + 種目数」ぶんの
読み取りが発生する。画面の前面復帰ごとに走らせると無料枠（1 日 5 万読み取り）を
無駄に削るので、**自動で走る同期には 60 秒の最小間隔**を入れてある。設定画面の
「いま同期する」はこの間隔を無視する。

Firebase SDK は動的 import で、`firestore/lite` を使っている（SDK 側の永続キャッシュは
使わない。ローカルの保存は自前の IndexedDB が持っているので二重に持つ意味がない）。

**種目は物理削除しない。** 削除は「無い」ことを表す更新を作れないので、
last-write-wins では次の同期で消したはずの種目が戻ってくる。`archived` の
切り替えなら普通の更新として伝わる。セッションを空にしたときは、空のセッションを
リモートに送って「消した印」にしている（取り込み側で落とすと両側が一致する）。

> **保存する条件と「消した印」の条件は必ず一致させる。** `isTombstone` は
> `worthStoring` の裏返しとして定義してある。別々に書いていたときは、
> 体重だけ付けた休養日が「消した印」と見なされ、**同期先の端末で体重が消えていた**。
> 保存する対象を増やすときは、片方だけ直すと記録が失われる。

### セットアップ

**同期が要らないなら丸ごと飛ばせる。** 入口で「鍵を使わずにこの端末だけで使う」を
選べば設定なしで使える。あとから鍵を作れば、それまでの記録ごと同期が始まる。

1. [Firebase Console](https://console.firebase.google.com/) で Firestore を有効化する
   （news-curator で作ったプロジェクトに相乗りしてよい）
2. **Authentication → Sign-in method → 匿名** を有効にする
3. プロジェクト設定 → アプリを追加 → ウェブアプリを登録し、`apiKey` / `projectId` / `appId` を控える
4. リポジトリの **Settings → Secrets and variables → Actions → Variables** に登録する

   | Name | Value |
   | --- | --- |
   | `VITE_FIREBASE_PUBLIC_API_KEY` | Firebase の apiKey |
   | `VITE_FIREBASE_PUBLIC_PROJECT_ID` | Firebase の projectId |
   | `VITE_FIREBASE_PUBLIC_APP_ID` | Firebase の appId |

   `PUBLIC` が付いているのは名前のとおり秘密にしなくてよい値だから。Firebase の
   apiKey はアクセス制御に使われず（制御は Security Rules 側）、ビルド済み JS に
   そのまま入って誰でも見られる前提の値。Secrets ではなく Variables に置くのは
   実態と合わせるため。

5. Firestore → ルール を貼って公開する

   **設定画面の「Security Rules をコピー」から、同期先 ID が埋まった文面をそのまま
   取れる**ので、それを貼るのが早い。中身はこの形になっている。

   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       match /vaults/{vault}/{document=**} {
         allow read, write: if request.auth != null && vault == '<自分の同期先 ID>';
       }
     }
   }
   ```

   **ID の固定は省略できない。** 匿名サインインは誰でも通せるので、`request.auth != null`
   だけを条件にすると、公開サイトを開いた人が自分の領域を作ってこのプロジェクトに
   書き込める。他人の記録は読めない（別の ID なので到達できない）が、容量と無料枠は
   消費され、あなたの同期が止まりうる。ID を固定すれば領域そのものを作れなくなる
   （拒否された要求は読み書きの課金対象にならない）。

   同期先 ID は鍵の SHA-256 で、**鍵と同じくらい秘密にする**（ID を知っている人は
   匿名サインインを通せば読み書きできる）。Security Rules はクライアントから読めないので、
   ここに書いても漏れない。

未設定でもアプリは動く。その場合は設定画面に同期が無効である旨が出て、
記録はこの端末だけに残る。無効の理由は「設定が入っていない」と「鍵を作っていない」で
書き分けている（`Sync.off`）——足すものが違うので、同じ文面にすると次の一手が分からない。

## 6. 記録を Claude に渡して相談する

「記録」画面の「記録を渡して相談する」を押すと、期間ぶんの記録・種目の設定・コツ・メモ・
体重の推移を積んだ状態で Claude の新規チャットが開く。期間は 4 週間 / 12 週間 / 全期間。

依頼文は**ボディメイクを目的にした語りかけ**を求める形にしてある。数字を並べた分析
レポートを返されると読まなくなって形骸化するので、次のように頼んでいる。

1. 続いていること・変わったことを、記録から具体的に 2〜3 個
2. 見た目の観点で次に効く一手を 1〜2 個だけ（多いと動けない）
3. バランスの偏りを 1 つだけ
4. 次にジムへ行くときに思い出せる短い言葉

API は使わない。プロンプトをクエリに載せた URL を開くだけなので、鍵も費用もかからず、
ログインしている本人のアカウントでそのまま会話が始まる。iOS / Android ではこの URL が
Claude アプリの Universal Link になっているのでアプリが開く。デスクトップアプリは
claude.ai のリンクの受け皿にできないので、押したときに同じ内容をクリップボードにも
入れている（アプリに貼れば続けられる）。

URL に載せられる長さには上限がある。日本語は 1 文字が `%E3%81%82` の 9 文字になるので、
種目名とメモが効く。上限を超える場合は優先度の低い節（メモ → コツ → 古い種目）から
落とすが、**クリップボードには常に全文が入る**ので、貼れば失われない。

## 7. デザインの方針

コンセプトは「洗練された上質な肉体を作るためのトレーニングプロデュース」。
`src/styles.css` の冒頭にも同じことを書いてある。

1. **完全な無彩色 + 赤 1 色。** ベージュや焙煎色のような色味を地に置くと、それ自体が
   主張して記録の数字より先に目に入る。地は無彩色に徹して、色は赤だけに任せる
2. **赤は面ではなく信号として使う。** ヘッダを赤で塗る作りは目立つが安くなる。
   「記録を更新した」「前回より伸びた」「今日である」だけに赤を割り当て、
   それ以外は無彩色。右下（実際には左下）の追加ボタンのような、まだ何もしていない
   操作には一番強い色を渡さない（地と反転した無彩色にしている）
3. **書体はゴシック 1 系統だけ。** 明朝を混ぜると和の情緒が出て、淡々と数字を置く道具という
   性格から外れる。字間の演出も最小に留めた。外部フォントは読み込まない
   （オフラインで動くことと、初回表示の速さを崩さないため）
4. **文字で説明せず記号で示す。** タブ・メモ・増減・前回・閉じるといった繰り返し出る
   ラベルはアイコンに置き換えた（`src/components/Icon.tsx`）。逆に記録の数字とコツの文章は
   文字のまま残す（記号にすると意味が伝わらない）。部位も色の点ではなく漢字 1 文字で示し、
   カレンダーは角丸タイルではなく罫線の格子にした
5. **達成の色に緑を使わない。** 赤と緑の信号色はどのフィットネスアプリにもある。
   赤が入る = 前進した、無彩色 = 変化なし、という 1 軸に寄せる

祝福の演出は、細い線が外へ走って消えるだけにしてある。紙吹雪のような賑やかな演出は
この画面の静けさから浮く。`prefers-reduced-motion` では線を出さない。

### 細部の決めごと

見た目の印象より、指と目に効く部分を実測して決めている。

- **色の役割を 2 つに分けた。** `--faint` は飾りと記号だけに使い、文字を載せない
  （以前は 2.3:1 しか出ておらず、前回の値や件数が沈んでいた）。塗りの赤と
  小さな赤文字も分けてある（`--accent` / `--accent-text`）。塗りの赤のまま小文字にすると
  暗い地で 3.8:1 しか出ず、明るくすると今度は白抜きの文字が弱くなるため
- **当たり判定は見た目を変えずに広げる。** メモの丸（28px）や閉じる（36px）は、
  透明な当たり判定を外へ伸ばして 44px 相当にしてある。セット行の高さは 44px。
  数値欄の幅は「62.5」が収まることを優先しているので、稼ぐのは高さ側
- **数字の欄は触ると空になる。** 前回の数字を消してから打つことがほとんどなので、
  選び直す手間を省く。元の数字は影（プレースホルダ）で残し、**打たずに離れたら
  元に戻す**——ここで最小値に落とすと、隣を触るつもりの一撫でや変換の取り消しで
  記録が消える。0 にしたいときは 0 と打つ（どの欄も `min` は 0）
- **入力の見せ方は 2 通りだけ。** カードの中（記録に添える文章）は**下線だけ**、
  シートの中（種目の設定）は**枠付き**。カードという枠の中にさらに枠を置くと、
  四角が入れ子になって記録そのものが埋もれる
- **記号と文字で同じことを言わない。** 部位の漢字 1 文字は、名前が出ない場所
  （種目カードの見出し）専用。一覧やシートの見出しは文字があるので記号を置かない
- **同じ重さのボタンを並べない。** 鍵を消す操作は「表示する」と並べず、
  文字だけの静かな操作にして一段挟む。押し間違いで同期先に戻れなくなるため
- **取り消せない操作は「何が失われるか」を出して一段挟む。** 種目を外すときの問いかけは
  「よろしいですか」ではなく「2 セットの記録と 1 件のメモが消える」と数を出す。
  焦点は最初から「やめる」に置き、危ない側は必ず右に置く。Escape と地の部分でも閉じる
- **同じ操作の入口を 2 つ並べない。** 追加ボタンは、末尾の普通のボタンが見え始めた時点で
  浮いている方を引っこめる。判定は末尾のボタン自身を見張る（`IntersectionObserver`）ので、
  記録が増えて高さが変わっても表示とずれない。スクロールが要らない短い日は、
  最初から末尾のボタンだけになる
- **キーボードで辿ったときだけ枠を出す**（`:focus-visible`）。ブラウザ既定の枠は
  この配色では見えないことがある
- **安全域は外枠で 1 回だけ持つ。** `viewport-fit=cover` を指定しているので、
  これが無いとホーム画面から起動したときに上部バーが時計やノッチの下へ潜る
- 触った瞬間の反応を少しだけ遅らせている（✓ は 140ms、節の展開は 200ms）。
  即座に切り替わると機械的に見え、長いと待たされる

### 広い画面（Web）

**スマホで詰めた寸法は動かさない。** 実機で決めた当たり判定と行の高さを、画面が
広いという理由で崩さない。足すのは 2 段だけで、どちらも `@media (min-width: …)`
の中にしかない。

| 幅 | 変わること |
| --- | --- |
| 〜60rem（960px） | スマホと完全に同じ。タブレットの縦（768px）もここ——指で使う幅では下の帯のほうが近い |
| 60rem〜 | 行き先が下の帯から**左の筋**へ移る（記号に字が付いて縦に積む）。セットの行が**1 行に畳まれる**。シートが中央の札になる。設定の横幅いっぱいのボタンが字の分の幅に縮む |
| 72rem〜（1152px） | 面が**2 列**に割れる。今日＝種目｜日付と要点、記録＝カレンダー｜最近の記録、体重＝折れ線｜一覧 |

考えたことをいくつか。

- **2 列を 60rem から始めない。** そこで割ると本文の列が 23rem しか残らず、
  **スマホより狭くなる**。広くしたのに窮屈になるのでは逆行になる
- **入力欄は伸ばさない。** 幅が余ったからといって数字の欄を広げても読みやすく
  ならない。「32.5」の右に空白が広がるだけなので、余りは数字の**意味**
  （実効負荷・前回との差）を横に並べるほうに使う
- **右の列は貼り付けて残す**（`position: sticky`）。種目を送っているあいだも
  日付と要点とメモが視界にあるので、いま何日のどこを見ているのか確かめに戻らない
- **カレンダー側は広げない。** 日の枠は正方形なので、列を広げると 1 マスが巨大に
  なって「月を一目で見る」道具でなくなる。余った幅は右の一覧に回す
- **設定は 40rem で止める。** 1 行が 60〜70 字を超えると読み返す位置を見失う
- **段の数を幅ごとに決めない。** セットの行は幅を固定しない要素を並べてあるので、
  入りきる画面では 1 行に、狭ければ自分で折り返す。前回との差を省略記号で
  切るより、行が増えるほうがまし
- 束ねるためだけに足した `div`（`.shell` / `.session-aside` など）は狭い画面では
  `display: contents` で**無かったことになる**。だからこれらを足しても
  スマホの見た目は 1px も変わらない
- タブの名前は常に DOM にあり、狭い画面では見えなくするだけ（読み上げには残る）。
  `display: none` だと押せるものの名前が消える。記号側に名前を持たせないのは、
  広い画面で字と記号が同じことを 2 回言わないため

**タブは横スワイプで移動でき、指に追従して面がスライドする。** 隣の面は指を動かし始めた
時点で用意し、離した時点で移動量（画面幅の 26%）か速さで切り替えるか戻すかを決める。
最初のわずかな動きで縦横どちらの操作かを判定し、縦と決まった指では何もしない
（`touch-action: pan-y` で縦は素の挙動に任せ、横だけ JS が扱う）。入力欄・シート・数値欄の
上から始まった操作は無視する。端では動かさない——動かないことで端だと分かる。

**画面の骨格は app-shell 型。** 文書そのものはスクロールせず、面の中だけがスクロールする。
そのためタブバーはスクロールに関係なく常に同じ位置にいる。上部の帯は面の中で sticky。

**拡大操作は止めてある。** viewport の `user-scalable=no` に加えて、iOS Safari は
これを無視することがあるので Safari 独自の gesture イベントも潰し、二度叩きの拡大は
`touch-action: manipulation` で止めている。入力欄に触れたときの自動拡大も起きなくなる。

**種目の追加ボタンは左下に固定してある。** セット行の ✓ は右端に並ぶので、右下に置くと
スクロール位置によって ✓ の上に重なる。✓ は 1 セッションに何十回も押す操作で、種目の追加は
数回。頻度の低い操作を遠い側に置いて、頻度の高い操作を塞がないほうを取った。

**日付は 1 行に収める。** 日付・曜日・「今日」を縦に積むと視線が縦に動く。曜日だけ
カレンダーの慣習に合わせて**土は水色、日は赤**にしてある（祝日は扱わない）。
この 2 色が「無彩色 + 赤」の唯一の例外。休日の区別は色以外に置き換えが効かない
（文字を足すと画面が説明で埋まる）ので、意味のある色として通した。使うのは曜日の
1 文字だけに限っている。

**上部の帯は面の中で固定して追従する。** 体重はトレーニングをしない日にも入れるものなので、
スクロールした先からでも届く位置に置いた。

「体重」の字は数値欄のすぐ左に、間を詰めて置いてある。離すと右上の数字が何なのか
結びつかない（実際に分からないという指摘を受けて直した）。直近の値は**今日まだ入れていない
ときだけ**、「前回」と日付を添えて出す。素の数字だけでは何なのか伝わらないし、今日ぶんを
入れたあとは同じ数字が 2 つ並ぶだけになるので消える。

アイコンは**バーを担いだ V**。上の横棒がバーベル、下が V で、V は肩幅から腰へ絞る
逆三角形のシルエット。バーが V の肩幅より少し外へ出ているのは、実際に担いだときの
見え方に合わせたもの。

**定型の三角をやめた理由。** 最初は三角形（＋水準を表す線）で組んでいたが、三角形は
輪郭が一般的すぎて何のしるしにも見えない。中に逆三角形を抜く案も試したが、
外形が定型の三角のままで、抜いた窓は小さいサイズで消える。バーと V の 2 要素にすると
固有の輪郭になり、間の余白も意味を持つ（担いでいる、という関係が余白で読める）。
18px でも形が保つことを実測で確かめてから決めた。

V は**ワードマークの V と同じ字形**を使っている。印と字で同じことを言い、内側の谷の
深さも同じ比率（高さの約 60%）に揃えてある。器具そのものの絵にしなかったのは、
道具の説明になってしまい「produce する」立場が出ないため。

角はすべて丸めてある。塗りと同じ色の線を重ねて（`stroke-linejoin: round`）落としている。
数学どおりの鋭角は小さく描くと潰れて濁るため。

`scripts/make-icons.mjs` が図形から PNG を直接生成する（SVG 変換ツールは環境によって
入っていないので、依存を増やさずどこでも同じ絵が出るようにした）。`npm run icons` で作り直せる。

## 8. オフライン

- **アプリ本体**: Service Worker が dist の中身を全部プリキャッシュする。2 回目以降は
  圏外でもホーム画面から起動できる
- **記録**: IndexedDB。書き込みにネットワークは一切関わらない。触った時点で保存される
  （保存ボタンは無い）
- **更新**: 新しい版が来ても自動で再読み込みしない。セットの途中で画面が入れ替わるのが
  一番困るので、バナーを出して押すまで待つ

Workbox は入れていない。やることが「dist を全部プリキャッシュする」だけなので、
生成された `dist/sw.js` をそのまま読んで理解できる状態のほうがよい。
ハッシュ付きファイル名は事前に分からないため、`vite.config.ts` のプラグインが
ビルド後に `public/sw.js` のプレースホルダを実際の一覧へ置き換えている。

IndexedDB が開けない/固まっている環境では、4 秒で諦めてメモリだけで動かし、
設定画面に「保存できていない」と出す。`indexedDB.open` は success も error も blocked も
飛ばないまま黙り込むことがあり、待ち続けると起動画面のまま何も出ない状態になるため。

## 9. 使い方

```bash
npm install
npm run dev        # http://localhost:5180/overload/
npm test           # 計算部分の単体テスト
npm run typecheck
npm run build && npm run preview   # Service Worker の確認はこちら
npm run icons      # アイコンを再生成する
```

dev サーバーでは Service Worker を登録しない（`public/sw.js` が置換前のままなので）。

### GitHub Pages に出す

1. リポジトリを push する
2. **Settings → Pages → Build and deployment → Source** を **GitHub Actions** にする
3. main に push すると `https://<ユーザー名>.github.io/<リポジトリ名>/` に出る

`base` はリポジトリ名から決まる（`BASE_PATH` で上書きできる）。同期を使うなら
「5. 同期」のセットアップも行う。

> GitHub Pages を private リポジトリで使うには有料プランが必要。無料プランなら
> public リポジトリにする。記録はリポジトリに入らず、鍵もバンドルに入らないので、
> public でも記録が漏れることはない。

### ホーム画面に追加する

iPhone なら Safari で開いて共有 → ホーム画面に追加。以降は単体のアプリとして起動し、
圏外でも開ける。iOS では Safari と PWA で保存領域が別なので、**記録を貯めるのは
どちらか片方に決める**（同期を有効にしていれば、どちらでも同じ記録が開く）。

## 10. バックアップ

| --- | --- |

## 11. 構成

```
src/lib/          UI から独立した計算とデータ層（ここだけテストがある）
  types.ts        ドメインの型。ID はブランド型。部位・筋肉・負荷のかけ方を各 1 箇所から導出
  progression.ts  実効負荷・推定 1RM・前回との比較・停滞判定
  records.ts      記録更新の判定（祝福を出す条件はここだけで決まる）
  presets.ts      初期種目 40 とその説明（やり方・効く筋肉・コツ）
  calendar.ts     日付計算。すべてローカルタイムの 'YYYY-MM-DD' 文字列で完結させる
  query.ts        セッション群から「前回どうだったか」「その日の体重」を引く
  sync.ts         ローカルとリモートの突き合わせ規則（ネットワークに触らない）
  askClaude.ts    Claude に渡すプロンプトの組み立てと長さの調整
  migrate.ts      保存済みデータを現在の形に揃える（読み出しの入口 1 箇所）
  vault.ts        鍵の発行・正規化・同期先 ID の導出
  db.ts           IndexedDB。開けない環境では 4 秒で諦めて UI に伝える
  remote.ts       Firestore（Firebase SDK は動的 import）
  backup.ts       書き出し・読み込み（手書きの検証つき）
  updates.ts      Service Worker の登録と更新通知
src/store.tsx     ローカルの状態と IndexedDB への保存
src/sync.tsx      同期の進行役（いつ走らせるか）
src/components/   画面。BodyMap.tsx が効く筋肉の図、Icon.tsx が線画のアイコン、
                  Celebration.tsx が記録更新の祝福、BodyWeightView.tsx が体重の折れ線
public/sw.js      Service Worker（プレースホルダはビルド後に置換される）
scripts/          アイコン生成
```

日付を `Date` に入れて戻す往復はしない。タイムゾーンで 1 日ずれる事故が起きるので、
`'YYYY-MM-DD'` 文字列のまま計算する（`calendar.ts` にテストがある）。

並べ替えと体重の引き当ては、セッション配列の同一性で結果を使い回している（`query.ts`）。
種目カードごとに全セッションを並べ替え、その中で 1 日ずつ体重を線形探索していたため、
記録が増えると種目数 × 日数の二乗で効いていた。配列は保存のたびに作り直されるので、
中身が変われば勝手に作り直される。

`presets.ts` は手書きのデータが 40 件あるので、整合性を機械で見ている
（id の重複・レップ範囲の逆転・説明の欠落・主働筋と補助筋の重複など）。
綴り間違いは型が捕まえるが、これらは型では通ってしまう。

保存済みデータの読み出しは必ず `migrate.ts` を通す。項目を後から足したとき、
`set.note ?? ''` のような防御を各所に散らすと必ずどこかで漏れるので、
入口を 1 箇所にして以降は全項目が揃っている前提で書いている。

## 12. v0.4 に入っていないもの

- **同じ日の同じ種目を 2 台で同時に編集したときの解決**。last-write-wins なので

- RPE・セットの種類（アップ / メイン / ドロップ）の区別
- 種目の並び替え（今は「最近やった順 → プリセットの並び」で自動）
- 休憩タイマーの通知音。バックグラウンド通知は iOS の PWA では当てにならないので、
  鳴る前提の機能にしていない（画面上のカウントアップだけ）
